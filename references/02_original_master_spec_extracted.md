٢. الملخص التنفيذي

HOTEL PMS SAAS هو نظام إدارة فنادق احترافي يعمل كمنصة سحابية متعددة العملاء، بحيث يمكن للمنصة المركزية إدارة عدد كبير من الفنادق مع عزل كامل وصارم لبيانات كل عميل، مع دعم الوصول المتعدد للمستخدمين والمواقع والعمليات التشغيلية والمالية والتقارير والتكاملات.

القرار المعماري الأساسي هو البدء بمنصة متجانسة معيارية ذات حدود Domain واضحة، بدلاً من البدء بخدمات صغيرة مستقلة كثيرة. الغرض هو الحفاظ على الاتساق القوي في العمليات التي تتطلب ذلك، مثل الحجز وتخصيص الغرفة والدخول والمغادرة والفوترة والدفع والتدقيق الليلي، مع بناء حدود داخلية تسمح بفصل التقارير والعمال الخلفيين والتكاملات عندما يفرض الحجم ذلك.

٤. الرؤية والهدف التجاري

٤.١ تعريف المنتج

النظام هو منصة تشغيل فندقية مركزية توحد عمليات الحجز والاستقبال والغرف والنزلاء والتدبير الفندقي والصيانة والحسابات والفوترة والمدفوعات والإغلاق الليلي والتقارير، مع طبقة SaaS مستقلة تدير العملاء والاشتراكات والميزات والحدود.

٤.٢ المشكلات التي يحلها المنتج

منع تعارض الحجز وتجاوز المخزون القابل للبيع بسبب عمليات متزامنة.

منع الأخطاء المالية الناتجة عن التعديل المباشر أو إعادة إرسال طلب الدفع.

توحيد دورة الضيف من الحجز حتى المغادرة والتسوية.

تقليل الاعتماد على العمل اليدوي بين الاستقبال والتدبير الفندقي والصيانة والمالية.

توفير سجل يمكن تدقيقه لمن غيّر ماذا ومتى ولماذا.

تقديم منصة واحدة قابلة لإدارة عدة فنادق دون خلط بياناتها.

٤.٤ ما الذي يجعل المنتج SaaS حقيقياً؟

التنصيب والنشر مركزيان ولا يحتاج كل فندق إلى نسخة منفصلة من التطبيق الأساسي.

كل عميل يمتلك Tenant مستقلاً، مع إعداداته ومستخدماته وفنادقه واشتراكه وميزاته.

الخدمات المشتركة مثل الهوية والمهام الخلفية والمراقبة يمكنها خدمة أكثر من عميل دون كسر العزل.

توجد حدود استخدام واشتراكات وميزات يمكن تغييرها دون تعديل جوهر النظام.

يمكن تشغيل عشرات أو مئات العملاء على البنية نفسها، ثم نقل العملاء الكبار إلى طبقة استضافة مخصصة لاحقاً عند الحاجة.

٦.٢ ما يوصى بإضافته بعد ثبات النواة

الحجوزات الجماعية المتقدمة، قائمة الانتظار، قواعد الأسعار الموسمية المتقدمة، التقارير المجدولة، تحسينات التدبير والصيانة، والتحليلات التجارية.

٦.٣ ما يُؤجل عمداً

التفعيل الكامل لجميع القنوات الخارجية لا يبدأ قبل اكتمال محرك الغرف والأسعار والتوفر والحجوزات، لكن بنية مدير قنوات البيع والتوزيع وعقودها ومخزن الخرائط يجب أن تُؤسس مباشرة بعد أساس المنصة. أما التغطية الواسعة جداً للقنوات، إدارة الإيرادات الديناميكية، برامج الولاء، المشتريات والمخزون العام، والذكاء الاصطناعي التنبؤي فتأتي لاحقاً وفق أولوية المنتج.يد قبل ثبات العمليات الأساسية.

٦.٤ قاعدة ضبط النطاق

قاعدة الأولوية الجديدة: مدير قنوات البيع والتوزيع ليس وظيفة مؤجلة في التفكير المعماري. يتم تثبيت حدوده وعقوده ونموذج الخرائط واستراتيجية المزامنة مباشرة بعد تأسيس المنصة، ثم يتم تفعيله فعلياً بعد جاهزية الغرف والأسعار والتوفر والحجوزات.

| قاعدة / أي وظيفة لا تؤثر مباشرة في سلامة الحجز أو التشغيل أو المال أو العزل الأمني أو القدرة الأساسية على إدارة الفندق لا تدخل الإصدار الأول إلا بقرار منتج موثق يبرر الحاجة. |
| --- |

٧. تحليل مجال الفندق ودورة التشغيل

دورة التشغيل يجب أن تُفهم كسلسلة مترابطة وليست مجموعة شاشات مستقلة. كل مرحلة تغير حالة أو حقيقة يجب أن تحترم قواعد المرحلة السابقة وتنتج أثراً واضحاً للمرحلة التالية.

| المرحلة | القواعد الأساسية | النتيجة المطلوبة |

| الحجز | التحقق من التوفر والسعر وسياسة الإلغاء والبيانات المطلوبة. | حجز بحالة واضحة |

٩. نموذج المنصة متعددة العملاء

٨.١ مدير قنوات البيع والتوزيع — أولوية ما بعد الأساس

هذا المكوّن يبدأ تصميمه مباشرة بعد تأسيس المنصة الهندسية، حتى لا يُبنى محرك الحجوزات لاحقاً بشكل يصعب ربطه بالقنوات. التفعيل التشغيلي للقنوات يعتمد على اكتمال Property وRoom Type وRate Plan وAvailability وReservation Contracts، لكن عقود التكامل ونموذج البيانات وحدود العزل والتزامن تُحسم مبكراً.

Core PMS

ممنوع الاعتماد على الكشط أو محاكاة المتصفح كقاعدة Core للتكاملات التجارية. الأولوية للاتصالات الرسمية أو موفري الاتصال المعتمدين، مع إبقاء Adapter Boundary بحيث يمكن تغيير مزود الاتصال دون تغيير Core PMS.

تجب كذلك بنية خرائط مستقلة تربط نوع الغرفة وخطة السعر في PMS بما يقابلهما في كل قناة. ولا يجوز افتراض تطابق أسماء الغرف أو خطط الأسعار بين الأنظمة.

قواعد التصميم: القنوات لا تدخل إلى Core Database مباشرة؛ كل قناة تستخدم Adapter مستقلاً؛ جميع الحجوزات الخارجية تتحول إلى نموذج Reservation موحد؛ المزامنة Idempotent؛ لكل رسالة خارجية معرف خارجي؛ وكل خطأ قابل لإعادة المحاولة دون تكرار مالي أو تشغيلي.

٩.٣ لماذا هذا النموذج؟

يقلل تكلفة التشغيل مقارنة بقاعدة منفصلة لكل عميل، ويسهل النشر والترقية والمراقبة.

يبقي عدد الكيانات والبنية موحداً ويمنع تكرار مخطط قاعدة البيانات لكل عميل.

يمكن إضافة مسار مخصص للعملاء ذوي المتطلبات الأعلى دون إجبار جميع العملاء على تكلفة البنية نفسها.

٩.٥ القاعدة الصارمة

لا يجوز اعتبار Tenant ID الذي أرسله العميل في الطلب حقيقة موثوقة. الخادم يجب أن يستنتجه من الهوية والعضوية والسياق المصرح به، ثم يمرره إلى طبقة البيانات، مع وجود حماية قاعدة البيانات كطبقة دفاع إضافية.

١٠.٢ مبدأ المعاملات

المعاملة يجب أن تغطي التغيير الذي يجعل الحقيقة الداخلية صحيحة، بينما الأعمال الجانبية مثل إرسال الرسائل أو تشغيل تقرير ثقيل تُدفع إلى طابور بعد نجاح العملية الأساسية. هذا يمنع فشل قناة الإشعار من التسبب في rollback لعملية الحجز أو الدفع.

١١.١ قواعد حذف البيانات

الحذف الفعلي يُمنع في السجلات المالية وسجل التدقيق والعمليات الليلية.

تعطيل المستخدم أو الغرفة أو خطة السعر يتم عبر حالة فعالة/غير فعالة بدلاً من كسر التاريخ.

حذف Guest لا يُنفذ بطريقة تكسر سجل الإقامات؛ يجب وجود سياسة احتفاظ وخصوصية مستقلة تحدد متى وكيف تتم المعالجة.

| المشكلة | المنع المطلوب | الوسيلة |

١٣.٥ الغرفة ليست الحجز

١٤. الغرف والمخزون والحالات التشغيلية

١٤.١ أبعاد الحالة

| البعد | أمثلة | وظيفته |
| --- | --- | --- |
| الحالة الفيزيائية | نشطة، غير نشطة | هل الغرفة موجودة في المخزون التشغيلي؟ |
| حالة التدبير | متسخة، قيد التنظيف، نظيفة، مفحوصة | هل الغرفة جاهزة من ناحية Housekeeping؟ |
| حالة الصيانة | لا مشكلة، صيانة، خارج الخدمة، خارج الطلب | هل توجد قيود صيانة على بيع الغرفة؟ |
| حالة الإتاحة | محموزة، مشغولة، محجوزة/محجوبة زمنياً | هل توجد التزامات حجز خلال الفترة المطلوبة؟ |
| قابلية البيع | قابلة للبيع/غير قابلة للبيع | الناتج النهائي الذي تستخدمه محركات المخزون والحجز. |

١٤.٢ قاعدة قابلية البيع

قابلة للبيع = غرفة نشطة + ليست خارج الطلب + ليست خارج الخدمة + غير محجوبة + لا يوجد تعارض إقامة للفترة المطلوبة + المخزون يسمح بالبيع

هذه القاعدة تمنع الخلط بين كون الغرفة نظيفة وبين كونها متاحة للبيع، كما تمنع اعتبار الغرفة المشغولة أو المحجوزة نظيفةً أو غير نظيفة على أنها تعريف كامل للإتاحة.

١٧.٢ مبادئ موظف الاستقبال

أقل عدد ممكن من الخطوات للعمليات المتكررة، وضوح الحالة الحالية، منع الإجراءات المدمرة دون تأكيد وصلاحية، وإظهار التعارض فوراً بدلاً من إخفائه خلف عمليات لاحقة.

١٧.٣ اللغات واتجاه الواجهة

اللغة الأساسية للواجهة في المشروع يمكن أن تشمل العربية والإنجليزية والإندونيسية، مع دعم اتجاه RTL للعربية وLTR للغات الأخرى. النصوص والعناوين وقواعد التنسيق يجب أن تأتي من طبقة توطين وليس من منطق المجال.

٢٣.١ مدير قنوات البيع والتوزيع

مدير قنوات البيع والتوزيع هو طبقة توزيع مستقلة تحفظ Core PMS من الارتباط بتفاصيل مزود واحد. وظيفته أن يأخذ الحقيقة الداخلية للغرف والأسعار والتوفر والحجوزات، ثم يترجمها إلى عقود كل قناة، ويعيد تطبيع الحجوزات والتعديلات والإلغاءات الواردة إلى نموذج موحد داخل PMS.

٢٣.٢ ما يجب أن يدعمه من البداية

المخزون المركزي: المصدر الوحيد للتوفر القابل للبيع، مع توزيع الحصة أو التوفر لكل قناة وفق قواعد الفندق.

مزامنة الأسعار: نشر الأسعار وخطط الأسعار والتعديلات الزمنية والخصومات والقواعد المسموح بها.

القيود التجارية: الحد الأدنى للإقامة، الحد الأقصى، منع الوصول، منع المغادرة، وإيقاف البيع عندما يدعم المزود ذلك.

استقبال الحجز: استقبال Reservation جديدة وربطها بالمعرف الخارجي للقناة وتطبيع بيانات الضيف والغرفة والسعر.

التعديل والإلغاء: معالجة Modification وCancellation وNo-Show وفق تسلسل آمن ومقاوم للتكرار.

الخرائط: ربط Room Types وRate Plans وMeal Plans وسياسات الحجز بين PMS وكل قناة.

المزامنة ثنائية الاتجاه: ما يرسله PMS إلى القناة وما تستقبله المنصة من القناة يجب أن يكون قابلاً للتتبع.

إعادة المحاولة: فشل الاتصال لا يؤدي إلى فقدان العملية؛ الرسالة تنتقل إلى Retry/DLQ حسب نوع الخطأ.

المراقبة: إظهار حالة كل قناة، آخر مزامنة، عدد الرسائل الفاشلة، آخر خطأ، وزمن الاستجابة.

٢٣.٤ معمارية المزامنة

٢٣.٥ قواعد تمنع التكرار والتعارض

لكل حجز خارجي External Reservation ID فريد ضمن القناة، ويجب عدم إنشاء الحجز مرة أخرى عند إعادة إرسال الحدث.

كل عملية إرسال تحمل Idempotency Key أو معرفاً مكافئاً يسمح بإعادة المحاولة دون تكرار.

تغييرات المخزون تنفذ من مصدر مركزي واحد، ولا يتم السماح لكل قناة بأن تصبح مصدراً مستقلاً للحقيقة.

إذا حدث تعارض بين تغيرات متزامنة، يستخدم النظام ترتيباً واضحاً للأحداث مع حالة Sync Conflict قابلة للمعالجة والتدقيق.

لا تؤثر مشكلة قناة واحدة على قاعدة بيانات أو عمليات القنوات الأخرى، إلا في الحالة التي يفرضها التوافق الكامل للمخزون ويجري تسجيلها.

٢٣.٦ حدود التفعيل المرحلي

التصميم والتعاقد يبدأان في المرحلة الثانية من خارطة الطريق. أما الاتصال الحي بالقنوات فيبدأ بعد اكتمال نموذج الغرف والأسعار والتوفر والحجوزات. هذا الفصل يمنعنا من تأخير القرار المعماري، وفي الوقت نفسه يمنع تنفيذ تكاملات حية فوق نواة PMS غير مستقرة.

Core PMS
↓
Central Inventory / Rate State
↓
Distribution Orchestrator
↓
Channel Adapter
↓
Provider API

Inbound: Provider → Adapter → Normalize → Idempotency → Reservation/Change

يُبنى النظام بحيث يمكن إضافة القنوات التالية كمرحلة تشغيلية أولى ثم توسيعها تدريجياً: Booking.com، Traveloka، Agoda، Expedia، Trip.com، ثم أي قناة إضافية يتوفر لها اتصال رسمي أو موثوق. تُعامل القنوات كمزوّدات قابلة للتبديل، ولا ترتبط أسماءها أو خصائصها داخل Core Domain.

| التكامل | طريقة العزل |
| --- | --- |
| البريد | محول إرسال لا يدخل في منطق الحجز. |
| WhatsApp/SMS | قناة تنفيذ للحدث، مع retry وdead-letter عند الحاجة. |
| بوابات الدفع | Adapter يخفي تفاصيل المزود ويحفظ المعرفات الخارجية. |
| المحاسبة | Mapping للأحداث المالية إلى النظام الخارجي. |

| محرك الحجز | واجهة تجارية خارجية تستهلك عقوداً مستقرة من PMS. |
| مدير قنوات البيع والتوزيع | طبقة توزيع مركزية، لكل قناة Adapter مستقل، مع Idempotency وRetry وخرائط ومراقبة مزامنة. |

| قاعدة التكامل / لا يسمح لأي مزود خارجي بالوصول المباشر إلى جداول Core PMS. التغيير يمر عبر عقد تكامل واضح، تحقق، Idempotency، وتسجيل للأحداث الخارجية. |

٢٥.٢ اختبارات بوابة الإصدار

اختبار أن مستخدم العميل أ لا يرى مورداً من العميل ب حتى إذا عرف معرفه.

اختبار أن تكرار طلب الدفع بنفس المفتاح لا ينشئ عملية ثانية.

اختبار أن حجزاً متزامناً لا يسمح ببيع الغرفة نفسها مرتين.

اختبار أن Check-In المزدوج يفشل بشكل متوقع بعد نجاح العملية الأولى.

اختبار أن الإجراء المالي المصحح يحتفظ بالتاريخ الأصلي.

اختبار أن Night Audit لا يغلق يوماً بينما توجد معاملات غير معالجة خلافاً للسياسة.

٣٢.١ خطوات التنفيذ داخل كل مرحلة

الخطوة 1 — تثبيت هدف المرحلة وحدودها، وما هو خارج نطاقها.

الخطوة 2 — تثبيت الاعتماديات التي يجب أن تكون جاهزة قبل البدء.

الخطوة 3 — تثبيت الكيانات والعقود والملكية والمسؤوليات المتأثرة.

الخطوة 4 — تحديد حالات النجاح والفشل والاستثناءات وحالات التزامن.

الخطوة 5 — اعتماد نموذج الأمن والعزل والصلاحيات الخاص بالمرحلة.

الخطوة 6 — تحديد اختبارات القبول واختبارات التزامن والعزل قبل التنفيذ.

الخطوة 7 — تنفيذ المجال أولاً ثم طبقة التطبيق ثم الواجهة أو التكامل.

الخطوة 8 — إضافة السجل التدقيقي والمقاييس والتتبع والإنذارات.

الخطوة 9 — تنفيذ اختبارات التكامل وEnd-to-End وRegression حسب الخطورة.

الخطوة 10 — اجتياز بوابة الخروج واعتماد المخرج قبل فتح المرحلة التالية.

٣٥. الملخص المعماري النهائي

٣٥.١ صورة المنتج

منصة PMS تجارية متعددة العملاء، تدير عدة فنادق ومستخدمين وعمليات حجز وإقامة ومالية وتقارير، وتدعم إضافة قنوات خارجية دون ربط قلب النظام بمزود واحد.

٣٥.٢ صورة العزل

هوية → عضوية → عميل → منشأة → Permission → Resource → قاعدة البيانات → RLS → التخزين المؤقت → الملفات → Jobs → التقارير

٣٥.٣ صورة البيانات

Tenant → Property → Rooms/Rates → Guest → Reservation → Stay → Assignment → Folio → Financial Events → Invoice → Night Audit → Reports

٣٥.٤ صورة التشغيل

واجهة سريعة + API منضبط + Domain واضح + PostgreSQL موثوق + Redis محدود + Queue/Workers + Storage خاص + Observability

٣٥.٥ الصورة المالية

المال يمثل أحداثاً قابلة للتدقيق وليست حقولاً يتم تعديلها حتى تبدو صحيحة. التصحيح يتم عبر عكس أو تسوية موثقة، والمدفوعات والاستردادات مصممة لتكون مقاومة للتكرار.

٣٥.٦ الصورة المستقبلية

يمكن لاحقاً فصل التقارير والعمال والتكاملات أو إضافة قاعدة مخصصة لعميل مؤسسي دون تغيير جوهر نموذج المجال، لأن الحدود صممت من البداية حول المجالات وليس حول صفحات الواجهة.

٣٥.٧ الصورة الخاصة بمدير القنوات

المصدر المركزي للحقيقة هو PMS، بينما مدير القنوات هو موزّع ومطبع للتعامل مع الأسواق الخارجية. يجب أن يكون كل تغيير قابلاً للتتبع من الحدث الداخلي إلى القناة والعكس، وأن تكون كل محاولة قابلة لإعادة التنفيذ دون تكرار. هذا المبدأ يجعل إضافة قناة جديدة عملية إضافة محول اتصال ومجموعة خرائط واختبارات، بدلاً من إعادة بناء الحجز أو المخزون.
