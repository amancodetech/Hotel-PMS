# مراجعة إغلاق حجر G03-F3-A/F3-B

التاريخ: 14 سبتمبر 2026. المراجع: جلسة مراجعة مستقلة لم تنفذ الإغلاق. النطاق: [سجل الإغلاق](execution/G03-F3-A-B.md) وتكليف [مراجعة الحجر](44_g03_quarantine_followup_review.md)، دون تعديل كود أو اختبار أو وثيقة قائمة.

## الحكم

**G-03: ACCEPTED** (قبول محلي مستقل). أُعيد إنتاج الإغلاق بالكامل على قواعد مؤقتة كاملة الترقية، ولم يثبت أي تجاوز غير معالج لدوري التشغيل أو أي استدعاء Adapter لاتصال محجور. هذا القبول محصور في نطاق مراجعة 44: لا قبول إنتاجي، ولا اتصال قنوات حية، ولا تفويض لبدء P04 (يبقى قرارًا للمستخدم).

## المنهج

- لم يُعدَّل أي كود أو اختبار أو مهاجرة أو وثيقة قائمة؛ أُنشئت أدوات مراجعة جديدة فقط تحت `.local/verification/review-g03-closure/` (مستبعدة من الحزمة) وهذا التقرير.
- كل أداة أنشأت قاعدة `hotel_test_<runId>_...` خاصة بها، وزرعت بيانات اصطناعية قبل الترقية ثم رقّت فعليًا إلى آخر مهاجرة، وحذفت قاعدتها ولقطتها فقط في `finally`. لم تلمس قاعدة التطوير `hotel` ولم يُشغَّل خادم dev.
- أُضيف فحص هوية اتصال (`current_user`) في أول كل أداة لمنع نجاح وهمي بسبب سقوط URL إلى دور المالك.

## F3-A — سجل المخالفات مغلق على دوري التشغيل

الدليل الأساسي: تشغيل الأداة الأصلية كما هي دون تعديل:

```sh
node --env-file=.env .local/verification/review-g03-quarantine/reproduce.mjs
```

المخرج: `CONTROL PASS` (Outbox المخالف المباشر مخفي فعلًا) ثم فشل عند أول قراءة للسجل:

```text
DriverException: permission denied for table distribution_consistency_conflict
code: '42501' ... file: 'aclchk.c', routine: 'aclcheck_error'
```

الفشل رفض صلاحية فعلي وليس فشلًا بيئيًا: مهاجرات الترقية نجحت، وفحص الضابط الإيجابي قرأ جدول Outbox بنجاح قبله، ثم جرى التنظيف التلقائي للقاعدة واللقطة.

سبر مستقل على قاعدة كاملة الترقية (`adversarial-probe.mjs`): بلا سياق وداخل Tenant A ومع `hotel_test` و`hotel_api` كلها `42501`؛ `has_table_privilege` للقراءة/الكتابة/الحذف/`truncate` على السجل = false للجميع؛ RLS مفعّل بصفر سياسات؛ مالك الجدول `hotel` (المشغّل الموثوق للتسوية). الدوال الست جميعها `public_execute=false`، والدالة الباطنة `distribution_conflict_row_tenant` و`distribution_row_quarantined` غير قابلتين للتنفيذ من أي دور تشغيلي (`42501`)، و`distribution_quarantined` ممنوحة لـ`hotel_worker`/`hotel_test` فقط ولا تمنح أي وصول خام، وترمي `22023` لجدول غير معروف.

## F3-B — الاتصال المحجور وتوابعه

أداة مستقلة جديدة (نسخة موسعة تتخطى فحص F3-A عمدًا):

```sh
node --env-file=.env .local/verification/review-g03-closure/reproduce-f3b.mjs
```

النتيجة: **59/59** على قاعدة `..._closure_review` بعد ترقية حقيقية من `170000` ببيانات قديمة مختلطة. الجداول الأحد عشر كلها (connection, outbox, inbox, exception, dead_letter, dedup, sync_attempt, checkpoint, booking, capability, mapping): صفر صفوف لـ`hotel_worker` بلا سياق، وبسياق Tenant A، وبسياق العميل المطابق، ولـ`hotel_test`؛ وصف واحد للمالك. `distribution_work_tenants` لا يعيد العميل المحجور؛ `claimPendingAck` صفر وعدّادات ACK لم تتغير؛ `leaseDueOutbox` صفر؛ `DistributionRuntime.tick` أعاد `leased=0, processed=0` ولم يستدعِ الـAdapter لأي اتصال محجور؛ الدالة المحدودة تُرجع `true` للاتصال المحجور و`22023` لجدول غير معروف.

وتؤكده اختبارات الترقية الدائمة `pnpm test:distribution`: 48/48 في 11 حزمة، مع نجاح ترقية قاعدة `legacyTenant` وحفظ البيانات وثلاثة مراجع محجورة.

## السطح الجديد — سبر عدائي مستقل

`adversarial-probe.mjs` على قاعدة `..._closure_probe`: **56/56**، ومنهجية الأدلة:

| السطر | السلوك | الدليل المختصر |
|---|---|---|
| قراءة السجل | `hotel_worker`/`hotel_test`/`hotel_api` بلا سياق وبسياق A | `42501` من `aclchk.c`؛ لا منح جدولية |
| كتابة في نطاق محجور | إدراج Outbox/Inbox/capability/mapping/checkpoint/booking/dedup/sync_attempt | `42501` لكل الحالات (سياسة أو وسيط اشتقاق يفشل مغلقًا) |
| إعادة الربط بالأب | تحويل Outbox سليم إلى اتصال محجور | `42501` (`new row violates row-level security policy`) |
| تعديل/حذف صف محجور | `hotel_worker` مباشرة | 0 صفوف (لا خطأ، لا تسريب) |
| المالك: الحذف | صف غير `RELEASED` | `23514` |
| المالك: `TRUNCATE` و`TRUNCATE CASCADE` | مع صفوف محجورة | `23514` |
| المالك: قيمة ثالثة | `DISMISSED` → `23514`؛ `NULL` → `23502` | قيد `resolution_check` يمنع إسكات الحجر |
| الإفراج مع خلل قائم | `orphan_tenant` و`tenant_mismatch` | `23514` لكلاهما |
| الإفراج بسبب غير معروف | صف reason=mystery | `23514` فشل مغلق |
| بعد إصلاح البيانات | `RELEASED` ثم حذف | نجاح، مع `resolved_at`/`resolved_by`، و`tenant_id` لم يُعد نسبته |
| ما بعد الإفراج | الجذر المتسق يعود مرئيًا وقابلًا للحجز، والابن ذو المخالفة المستقلة يبقى محجورًا | connection=1, inbox=1 وclaimed=1، وoutbox المحجور=0 وغير قابل للحجز |

و`hotel_api` بلا أي منح على جداول `distribution_*`، والأدوار التشغيلية لا ترث أي عضوية دور (`pg_auth_members` فارغ)، ولا تملك `CREATE` على مخطط `public`.

## طبقات العزل — اختبار سلب إحدى الطبقتين

`layering-probe.mjs`: عُطِّل وسيط `distribution_fill_tenant` مؤقتًا على قاعدة مؤقتة، فظل إدراج Inbox في نطاق محجور مرفوضًا من سياسة RLS وحدها:

```text
42501 new row violates row-level security policy for table "distribution_inbox_revision"
```

ثم أُعيد الوسيط ورفض الإدراج مرة أخرى. أي أن الحجب لا يعتمد على طبقة واحدة، ولم يبقَ صف يتيم بعد السبر.

## المسار السليم ومسار pull

`pull-and-healthy-probe.mjs`: **9/9**. العميل السليم يُكتشف ويُحجز ويُمرر أفعاله إلى الـAdapter، بينما لا يُلمس الاتصال المحجور. المسار الحقيقي للعامل لا يستطيع تحميل الاتصال المحجور أصلًا (`findConnection → null`).

ملاحظة دقيقة (P2، دفاع في العمق): استدعاء `pullConnection` بسياق مُلفَّق ومباشر يصل إلى `adapter.pullRevisions` **قبل** كتابة الحفظ، لأن الاستدعاء يسبق المعاملة في `pull-service.ts:59`. عندها يفشل الحفظ مغلقًا (`42501 distribution tenant derivation failed`) ولا يُحفظ صف ولا checkpoint. لا يوجد مسار تطبيقي يستدعي `pullConnection` حاليًا (لا في API ولا Worker)، والوصول إلى السياق يتطلب قراءة اتصال محجور أصلًا. لا إصلاح مطلوب الآن، ويُوصى عند تفعيل pull ببوابة صريحة على حجر الاتصال قبل النداء.

- المستودع بلا أي commit: `git status --porcelain` يعرض كل الملفات untracked و`git diff --stat -- packages/backend/src/persistence/migrations` فارغ، فلا يصلح Git وحده كدليل. لا توجد لقطة بصمات كاملة من قبل الإغلاق في `.local` (المتوفر `CHECKSUMS.before.sha256` من مرحلة P01 فقط).

## القيود وإعادة الإنتاج

- لا commit ولا نشر ولا اتصال خارجي ولا قنوات حية؛ P04 غير مفوَّض.
- لم تُعد هذه الجولة اختبارات الواجهة البصرية ولا audit الاعتمادات ولا اختبارات الأعطال (`--faults`).
- فرق بيئي موثق: `.env` لا يحوي `TEST_ROLE_DATABASE_URL` المذكور في التكليف، بل `TEST_DATABASE_URL` و`API_DATABASE_URL`؛ استُخدم الأول لدور `hotel_test` والثاني لدور `hotel_api` مع فحص `current_user`. في أول تشغيل للسبر سقط دور `hotel_api` خطأً إلى المالك فظهر نجاحان زائفان (A8/B8)؛ صُحح السبر وأُعيد تشغيله بالكامل (56/56)، والانحراف موثق هنا.
- قاعدة التطوير `hotel` لم تُلمس (لا `db:migrate` عليها)؛ حُذفت كل قواعد السبر ولقطاتها، ولم يبقَ أي `hotel_test_%`.
- أدوات المراجعة: `.local/verification/review-g03-closure/{reproduce-f3b,adversarial-probe,pull-and-healthy-probe,layering-probe,migration-down-up-probe}.mjs` وسجلاتها `.log`. النتائج: `reproduce-f3b` 59/59، و`adversarial-probe` 56/56، و`layering-probe` 4/4، و`migration-down-up-probe` 5/5، و`pull-and-healthy-probe` 9/9؛ خرجت كلها بـexit 0.
- CHECKSUMS.sha256 لم يُعدّل بعد إضافة هذا التقرير؛ يبقى التحقق `sha256sum -c` ناجحًا لقائمة الملفات المسلَّمة، ويُترك تحديث البصمة لجلسة المنفذ التالية.
