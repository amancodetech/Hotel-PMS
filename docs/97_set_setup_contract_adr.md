# ADR SET-02: عقد وبيانات معالج إعداد المنشآت

الحالة: **PROPOSED DESIGN** ضمن SET-02 (عقد تصميمي + خطة ترحيل). لا يغيّر D-01..D-20 ولا ترتيب المراحل ولا العزل ولا النموذج المالي.
المرجع: [docs/94](../94_property_setup_and_inventory_plan.md) §4–§8، [docs/95](../95_set_ai_implementation_playbook.md) §5–§6، والعقد [set.openapi.json](contracts/set.openapi.json) 0.1.0.

## 1. النطاق

- 8 عمليات تصميمية: قوالب، قراءة/حفظ/حذف المسودة، معاينة، تنفيذ، جاهزية، محاكاة بيع.
- التنفيذ التدريجي: SET-03 يبدأ بالمسودة والقوالب، SET-04 بالدفعات، SET-05 بالكامل/الأجزاء/الأسرّة/الجناح، SET-06 بالتغييرات المؤرخة، SET-07 بالمكتب الأمامي والتقارير.
- لا تُعد العملية منفذة حتى تسجل بطاقة الحزمة واختباراتها ذلك.

## 2. قرارات التصميم

| # | القرار | المبرر والحدود |
| --- | --- | --- |
| S1 | **مسودة واحدة لكل منشأة** بنطاق `tenant_id + property_id`، مع `revision` يزيد عند كل حفظ مقبول و`updated_by_membership_id`. | يطابق «تعارض نسخة مع مقارنة» ويمنع فوز آخر حفظ بصمت. لا مسودة متعددة المستخدمين في V1. |
| S2 | **إنشاء المنشأة أولاً** عبر المسار الحالي `CreateProperty`، ثم ترتبط المسودة بها. «إضافة منشأة» → إنشاء SETUP (idempotent) → معالج. | يمنع مسار إنشاء موازياً ويحافظ على `property.tenant_code_unique`. لا شركة ضمنية. |
| S3 | **حفظ idempotent** عبر `api_idempotency` القائم بعملية `SaveSetupDraft`، ومفتاح مطلوب؛ نفس المفتاح بمحتوى مختلف → `IDEMPOTENCY_CONFLICT`، ونفس المفتاح بنفس المحتوى → إعادة الاستجابة. | يمنع ازدواج المسودات عند انقطاع الشبكة (SET-AT01). |
| S4 | **`If-Match: "revision"`** على الحفظ والتنفيذ؛ عدم التطابق → `412 SETUP_DRAFT_STALE` مع أحدث نسخة في التفاصيل للمقارنة. | فحص تفاؤلي صريح بدل آخر-يكتب-يفوز. |
| S5 | **معاينة محسوبة عند الطلب** بلا كتابة مخزون: توسيع النطاقات والاستثناءات وكشف التكرار والحدود. `preview_version` **بصمة sha256** لـ(رقم المسودة + المدخل المطبع + `inventory_version`) وليست عدّاداً؛ أي حفظ مادي يغيّر البصمة فتُبطل المعاينة السابقة، والتنفيذ يعيد حسابها ويرفض بـ`PREVIEW_STALE` عند عدم التطابق. | يمنع الاعتماد على معاينة قديمة أو عدّاد معاينات كدليل صلاحية؛ لا جدول preview جديد. |
| S6 | **التنفيذ داخل معاملة واحدة** يعيد التحقق من الصلاحية والنسخة والمعاينة والحدود والأرقام قبل أي كتابة، ويفشل مغلقاً بلا مخزون جزئي. | يطابق docs/95 §10 وSET-AT03/05. |
| S7 | **حدود الدفعة مستقلة وصريحة**: لا يُعاد استخدام `max_items_per_request` (خاصة ببنود الحجز). يُضاف عمود `max_setup_units_inline` إلى `property_limits_profile` بقيمة مبدئية 20 (أساس: تنفيذ ذري مقاس بمعاملة واحدة ومراجعة بشرية للمعاينة)، ويُفرض مع `max_resources` القائم. التجاوز يُرفض بوضوح `SETUP_BATCH_TASK_REQUIRED` حتى توجد مهمة خلفية منفذة ومختبرة (SET-04)؛ لا إنشاء جزئي صامت. | لا حدود منقولة من نطاق آخر ولا وعد بأداء غير مقاس. |
| S8 | **كتالوج القوالب خادمي في الكود** (ثابت مُصدَّر عبر `ListSetupTemplates`) يربط القالب بنوع `resource_type` القائم وافتراضيات آمنة. | لا هجرة إعداد؛ يمنع تثبيت الواجهة. التخصيص لكل مستأجر لاحقاً لا يحتاج تغيير عقد. |
| S9 | **طريقة التأجير** حقول مسودة: `EXCLUSIVE | WHOLE_OR_PARTS | BEDS` + `privacy_ack` إلزامي للأجزاء + `sharing_scope` و`beds_per_unit` للأسرّة + `guaranteed_specs`. عند التنفيذ تُبنى على `resource/product/product_resource_candidate/composition_version` القائمة، ولا محرك مخزون موازٍ. | يحافظ على D-02/D-03/D-05/D-20. |
| S10 | **الجاهزية تقرير وفرض محددان، وليست تفعيلاً**: `GetSetupReadiness` تعرض النواقص؛ الفرض الخادمي محدود بـ: (أ) `ApplySetupDraft` يرفض `SETUP_READINESS_BLOCKED` عند وجود نواقص مانعة، (ب) تحويل منشأة لديها مسودة مخزنة وغير مكتملة إلى `ACTIVE` يُرفض بالرمز نفسه في `UpdateProperty`. لا يُجمّد تشغيل المنشآت القائمة، وفتح البيع يبقى عبر خطط الأسعار/الفترات، وتفعيل القنوات يبقى ببواباته الخارجية. | يطابق docs/94 §4 وSET-AT14 دون كسر السلوك القائم: المنشأة بلا مسودة تُفعَّل كما اليوم. |
| S11 | **المحاكاة قراءة فقط** (`GET setup-simulation`) ولا تنشئ حجزاً/Hold/Block/قيداً. | يطابق docs/94 §5 (محاكاة المراجعة). |
| S12 | **المسودة لا تغيّر lifecycle المنشأة** ولا تُفقد تاريخاً: الحذف يمس المسودة فقط. | يطابق docs/94 §8. |

## 3. خطة البيانات والترحيل (SET-03+)

| الجدول/التغيير | الحزمة | القيود والعزل | الرجوع |
| --- | --- | --- | --- |
| `property_setup_draft` (id, tenant_id, property_id, revision, preview_seq, input jsonb, completed, created_at, updated_at, updated_by_membership_id) | SET-03 | PK id؛ unique `(tenant_id, property_id)`؛ FK مركب `(property_id, tenant_id) → property(id, tenant_id)`؛ FORCE RLS `tenant_isolation` + trigger منع تغيير tenant_id؛ منح `hotel_api` select/insert/update و`hotel_test` كامل | حذف الجدول فقط عندما لا توجد مسودات؛ forward fix أولاً |
| `api_idempotency` عملية `SaveSetupDraft` | SET-03 | القيد القائم `(tenant_id, operation, key, property_id)` | لا تغيير بنيوي |
| `property_limits_profile.max_setup_units_inline` (integer, default 20, check > 0) | SET-03 | عمود مضاف؛ لا يمس `max_items_per_request` | إسقاط العمود فقط إن لم تُستخدم قيمه؛ forward fix أولاً |
| أعمدة/جداول BEDS والخصوصية (مثل `resource.sharing_scope` أو جدول سمات) | SET-05 | قرار حقل نهائي بعد نموذج SET-01؛ يُقيَّد بنوع المورد ويُفحص قبل البيع | إضافة ثم backfill مضبوط ثم قيود |
| تغييرات مؤرخة (نسخ جديدة) | SET-06 | نسخ جديدة فقط؛ لا تعديل ماضي منشور | إبقاء النسخ القديمة |

قواعد ملزمة:
- لا تعديل هجرة مطبقة؛ هجرة جديدة لكل تغيير.
- backfill قابل للإعادة ومحدود، ولا استنتاج خصوصية من الأسماء.
- اختبار ترقية قاعدة اصطناعية + فحص القيود/RLS بدور التشغيل قبل أي تطبيق.
- `jsonb` للمسودة مقبول لأنها ليست سجلاً مالياً ولا مخزوناً؛ تُحوَّل إلى كيانات المجال عند التنفيذ فقط.

## 4. الأخطاء المعلنة

| الرمز | HTTP | الاستخدام |
| --- | --- | --- |
| `SETUP_DRAFT_INVALID` | 422 | حقول ناقصة/غير صالحة مع `issues[]` (حقل/خطوة/مجموعة) |
| `SETUP_DRAFT_MISSING` | 404 | معاينة/تنفيذ بلا مسودة |
| `SETUP_DRAFT_STALE` | 412 | `If-Match` غير مطابق أو المسودة حُذفت/أُعيد إنشاؤها بين القراءة والكتابة |
| `PREVIEW_STALE` | 412 | بصمة `preview_version` لا تطابق (مسودة/مدخل/إصدار مخزون تغيّر) |
| `SETUP_READINESS_BLOCKED` | 422 | نواقص مانعة عند التنفيذ أو عند تفعيل منشأة لها مسودة غير مكتملة |
| `SETUP_MODE_UNSUPPORTED` | 422 | طريقة تأجير غير منفذة بعد (الكامل/الأجزاء والأسرة في SET-05) — رفض صريح بدل دعم شكلي |
| `SETUP_BATCH_TASK_REQUIRED` | 422 | تجاوز حد التنفيذ المباشر قبل وجود مهمة خلفية مختبرة |
| `LIMIT_EXCEEDED` | 422 | تجاوز `max_resources` أو حدود المنشأة |
| `CONFLICT` (reason=`idempotency_key_reused`) | 409 | نفس المفتاح بمحتوى مختلف — مطابق لسلوك المراحل القائمة |
| `SETUP_APPLY_IN_PROGRESS` | 409 | تنفيذ متزامن لنفس المسودة (يُضاف عند SET-04) |
| `CROSS_SCOPE_REFERENCE` | 400 | مرجع موقع/مورد خارج المنشأة |
| `PERMISSION_DENIED` | 403 | صلاحية أو MFA/CSRF |

## 6. أسئلة مفتوحة لا تُفترض

1. **عرض «منطقة/منشأة كاملة» المركب** (docs/94 §2): لا يغطيه `EXCLUSIVE/WHOLE_OR_PARTS/BEDS` مباشرة؛ يحتاج قرار نطاق في SET-05/06 ولا يُنفَّذ ضمناً.
2. **ملكية المسودة**: قرار S1 (مسودة مشتركة للمنشأة) مقترح؛ إن أراد المستخدم مسودة لكل مستخدم فالتغيير يمس المفتاح والتفويض.
3. **حد التنفيذ المباشر**: القيمة 20 مبدئية وقابلة للضبط في `property_limits_profile`؛ تغييرها قرار منتج ولا يغيّر العقد. الأساس هو الذرية والمراجعة البشرية، وليس قياس أداء.
