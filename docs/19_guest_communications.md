# مراسلات الضيوف بعد الإطلاق الأولي

حالة: مواصفة نطاق معتمدة في D-15، وتنفيذها مؤجل إلى المرحلة 14 بعد الإطلاق الأولي. ليست ميزة منفذة ولا ادعاء بدعم أي قناة بعينها.

## الهدف والحدود

Guest Communications وحدة مستقلة تجمع، في مساحة عمل واحدة، مراسلات الضيوف المصرح بالوصول إليها من القنوات والحسابات المرتبطة. تتكامل مع Reservations وGuests وOperations وNotifications وDistribution، لكنها لا تنقل ملكية الحجز أو الرسائل إلى القناة الأخرى ولا تمنح صلاحية لم يوفرها المزود أو حساب المنشأة.

الحد الأدنى لـ CAP-17: صندوق وارد موحد، عرض مصدر الرسالة والمنشأة والحجز المرتبط، رد من داخل النظام عند الدعم الرسمي، تعيين موظف أو فريق، حالات Open/Pending/Closed، ملاحظات داخلية، تنبيه الرسائل غير المجاب عنها، وتحويل طلب الضيف إلى مهمة. القوالب والرسائل المجدولة تشمل أمثلة مثل تعليمات الوصول والتذكير والمغادرة، وتظل خاضعة لموافقة المنشأة وقدرة القناة وحالة الحجز وقت الإرسال.

خارج الحد الأدنى ما لم يعتمد لاحقاً: مركز اتصال صوتي، حملات تسويقية جماعية، Chatbot مستقل القرار، تحليل مشاعر ملزم، أو دمج هوية شامل بين Tenants. قبل CAP-17 تظل الرسائل في القناة الأصلية، ويعرض النظام قيد القدرة أو رابط متابعة رسمي عند توفره.

## مصفوفة قدرة الاتصال

لكل Connection تسجل بصورة مستقلة: استقبال الرسائل، إرسال الرد، بدء محادثة، سجل المحادثة التاريخي، المرفقات وأنواعها وحدودها، حالة الإرسال والتسليم، Webhooks أو polling، أفق إعادة الإرسال، رابط المتابعة الخارجي، والصلاحيات أو الموافقات المطلوبة. القيم Supported/Unsupported/Unknown/Not Authorized لا تختزل في Boolean واحد، ولها مصدر تحقق وتاريخ ونسخة عقد المزود.

إتاحة new/modify/cancel للحجز لا تثبت إتاحة المراسلات. لا يعلن النظام دعماً لـ Booking.com أو Traveloka أو tiket.com أو Agoda أو غيرها قبل تحقق رسمي حديث واختبار الاتصال المحدد.

## السياق وسير العمل

Conversation تنتمي إلى Tenant وProperty وConnection، وقد ترتبط بحجز أو نزيل أو طلب خدمة بعد تحقق المراجع. لا يدمج النظام Guest أو Conversation لمجرد تشابه الاسم أو رقم غير موثق. يمكن إبقاء Participant خارجياً غير مدمج وإحالته للمراجعة.

Message تكون Inbound أو Outbound أو Internal Note. الملاحظة الداخلية لا تصل إلى Adapter مطلقاً. حالات الإرسال المطلوبة والمُرسلة والمؤكدة والفاشلة أو المجهولة منفصلة. تعيين المحادثة وتغيير حالتها لا يغير حالة الحجز، وتحويل رسالة إلى Guest Request ينشئ مهمة مرتبطة دون محو الرسالة أو جعل المحادثة هي سجل تنفيذ المهمة.

## الثوابت والحماية

- كل قراءة ورد وتعيين وقالب وجدولة يتحقق من Tenant وProperty وConnection وPermission وحالة المجال.
- الرسالة الخارجية المكررة تنتج أثراً واحداً، والرد المعاد لا يرسل مرتين؛ هوية منع التكرار ونطاق المزود محفوظان.
- لا تظهر Delivered بلا إقرار يدعم هذه الدلالة. النتيجة المجهولة تخضع للمطابقة أو إعادة آمنة حسب عقد المزود.
- قبل إرسال رسالة مجدولة يعاد فحص الحجز والمستلم والقناة. إلغاء الحجز يوقف تعليمات الوصول، مع تسجيل السبب.
- محتوى المحادثات والمرفقات بيانات ضيف؛ يخضع للحد الأدنى من الوصول والاحتفاظ والتدقيق، ولا ينسخ كاملاً إلى Logs أو أحداث عامة.
- لا تخلط الملاحظة الداخلية بالرد الخارجي بصرياً أو تعاقدياً، ويظهر الجمهور المقصود قبل الإرسال.

## الواجهة والتشغيل

يعرض Unified Guest Inbox المصدر والحجز والتواريخ والوحدة وحالة التسليم والمسؤول ووقت آخر رسالة ومؤشر SLA. المرشحات حسب Tenant/Property/Connection والحالة والمسؤول لا توسع نطاق الصلاحية. بجانب المحادثة تظهر فقط بيانات الحجز والحساب والطلبات التي يحق للمستخدم رؤيتها.

يرصد التشغيل الرسائل غير المعالجة، فشل التوقيع أو Mapping، عمر المحادثة بلا رد، محاولات التسليم، DLQ، ومطابقة الحالات المجهولة. تعطل اتصال واحد لا يمنع صناديق بقية المنشآت أو العملاء.

## بوابة المرحلة 14

لا يبدأ التنفيذ الحي قبل نجاح نواة PMS وتكامل الحجوزات المقرر للإطلاق الأولي، وفق تعريف الإطلاق المحسوم في D-01 وdocs/23_v1_decisions.md. أول إطلاق لـ CAP-17 يحتاج Connection واحداً موثق الدعم، بيانات اختبار لا تخص نزلاء حقيقيين، اختبارات AT-31..35، عزل وصلاحيات، معالجة مرفقات عند إدراجها، مراقبة، Runbook تعطل، وسياسة احتفاظ معتمدة للسوق.

نجاح بوابة CAP-17 يعني إثبات الاستلام والرد والتعيين والتحويل إلى مهمة ومنع التكرار والعزل وحالات التسليم. لا يعني نجاح قناة واحدة اعتماد بقية القنوات.
