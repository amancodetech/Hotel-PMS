# PSR — مواصفات التنفيذ وضوابط المنفذ

التاريخ: 23 سبتمبر 2026. الحالة التصميمية: **DESIGN_READY**؛ بدأ التنفيذ المحلي بتفويض المستخدم، والحالة الفعلية في سجل PSR.
صدر لاحقاً في23 سبتمبر تفويض تنفيذ محلي صريح؛ وجود هذا الدليل وحده لا يمنح اعتماداً إنتاجياً أو تفويضاً خارجياً.

اقرأ [الخطة وتجربة الاستخدام](99_property_structure_and_setup_redesign_plan.md)، ثم هذا الملف، ثم [اختبارات القبول](101_psr_acceptance_cases.md)، ثم [سجل الاستئناف](execution/PSR-progress.md). [دليل SET](95_set_ai_implementation_playbook.md) حاكم لضوابط الباك إند والتشغيل. إذا تعارض نطاق PSR في docs/99 مع هذا الدليل، فهذا الملف يحدد **الدفعة الأولى فقط**؛ بقية التصور تبقى توسعات ولا تُنفذ ضمنياً. تعليمات المستخدم وقرارات D تتقدم على كليهما.

## 1. تعريف الدفعة الأولى

الهدف: إضافة المكان ووحداته وطرق حجزه في أربع خطوات مفهومة، مع حفظ نفس ضمانات المخزون والهوية والتاريخ. لا تختَر Stack جديداً، ولا تنشئ محرك مخزون أو تطبيقاً موازياً.

### اختيارات تصميم محددة لهذه الدفعة

هذه توصيات تنفيذية مثبتة في الخطة بتكليف تحسينها، وليست قرارات D جديدة أو تفويضاً بالتنفيذ. عند صدور طلب التنفيذ تُستخدم كافتراضات عمل ما لم يوجه المستخدم بغيرها.

| المعرف  | الاختيار                                                                         | الأثر                                                                                 |
| ------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| PSR-D01 | موقع عنوان واحد لكل منشأة في الدفعة الأولى؛ مبانٍ ومناطق وطوابق اختيارية تحته    | المواقع الجغرافية المتعددة S24 مؤجلة؛ لا تنشئ Tenant لكل موقع                         |
| PSR-D02 | توسيع location القائمة بـparent_id وkind وdisplay_order؛ لا جدول Site مستقل الآن | موقع المنشأة هو عنوان property؛ الشجرة تنظيم مكاني فقط                                |
| PSR-D03 | المساحات غير المباعة بيانات وصفية ذات مخطط مضبوط داخل تفاصيل الوحدة              | لا جدول مخزون Space ولا مهام تنظيف مستقلة لكل حمام الآن                               |
| PSR-D04 | الكود الداخلي فريد بالمنشأة؛ display_label رقم/اسم ظاهر قد يتكرر مع مسار مميز    | لا تعيد ترقيم resource.code القديمة ولا تكسر مراجع التكامل                            |
| PSR-D05 | يحتفظ resource_type بمعناه القائم؛ template مستقل في بيانات الإعداد              | جناح مستقل يمثل مورداً ROOM بوصف SUITE_STANDALONE؛ لا إعادة تفسير SUITE القديم المتصل |
| PSR-D06 | ثلاثة محاور: physical_template، booking_mode، selection_mode                     | تسمية المنشأة HOTEL/RESORT لا تحدد منطق الحصرية                                       |
| PSR-D07 | لا تحويل تلقائي بين مورد فيلا واحد وأجزاء قابلة للبيع                            | الطلب يُرفض بلا كتابة في هذه الدفعة؛ لا إصلاح شكلي بتغيير enum                        |
| PSR-D08 | الحجز الجماعي يستخدم المسار القائم؛ لا إنشاء Composition تلقائياً لكل مجموعة     | حفظ مدد الوصول والمغادرة لكل عنصر                                                     |
| PSR-D09 | الوظائف الحالية من SET تُعاد الاستفادة منها؛ الامتدادات بعقد v2 صريح             | المسودة المنفذة لا تصبح قابلة لإعادة apply                                            |
| PSR-D10 | لا دول/عملات تشغيل جديدة ولا لغات جديدة في هذه الدفعة                            | تصميم قابل للتوسعة؛ إبقاء D-17 وD-14 وسلامة مفاتيح اللغات الحالية                     |
| PSR-D11 | تظهر طرق الحجز التي يفرضها الخادم فعلياً فقط                                     | المنع المباشر في API إلزامي ولو أخفت الواجهة الخيار                                   |
| PSR-D12 | تحتفظ الشركة والمنتج والمورد والتركيبة بمعرفاتها                                 | النقل بين المنشآت/العملات/المناطق الزمنية ليس تحرير حقل عادي                          |

اختبار القبول لا يغير توصية إلى قرار مستخدم. القرارات التجارية الجديدة أو تغيير D أو ترحيل بيانات مستخدمة خارج التفويض تسجل BLOCKED_DECISION للجزء المتأثر فقط.

### تغطية السيناريوهات من docs/99

- داخل الدفعة: S01–04، S06–10، S12–14، S17، S34.
- نطاق جزئي معلن: S15 وصف مهد/سرير إضافي فقط؛ S19 بقع محددة بلا محرك أهلية مركبات جديد؛ S23 إعادة استخدام المجموعات؛ S25 الحجب القائم فقط؛ S26 وصف مرفق فقط؛ S28 رفض تغيير يخرق وعداً قائماً وإعادة استخدام النسخ المدعومة؛ S31 ضمن حدود الإقامة الحالية؛ S33 مسار النقل القائم فقط.
- مؤجل بالكامل: S05، S11، S16، S18، S20–22، S24، S27، S29–30، S32. اختبار رفض S29–30 مطلوب الآن وإن كان التنفيذ مؤجلاً.
- فئة فلل كاملة مستقلة مبنية من موارد VILLA منفردة ضمن S02/S04؛ فئة بدائل فلل مركبة S21 مؤجلة. لا تخلط الحالتين.

## 3. عقد بيانات التصميم v2

هذه مواصفة لإنتاج OpenAPI في PSR-02، وليست ملف API منفذاً. على PSR-02 إثبات تمثيل كل قاعدة أدناه في schema/DTO أو توثيق invariant خدمي لا يمثله OpenAPI. لا يخترع المنفذ حقولاً إلزامية من عنده.

### المسودة

- schema_version: العدد 2 مطلوب في الطلبات الجديدة؛ المسودات القديمة تعامل كـ1.
- draft_id وrevision وcompleted: خادمية؛ لا قبول قيم يضعها العميل لتجاوز حماية التنفيذ.
- property: الحقول الحالية ومعاني null/omitted تبقى كما في العقد الموجود؛ لا إسقاط حقول v1 أثناء صدى الخادم.
- locations: قائمة بعقدة client_ref فريد داخل المسودة، existing_location_id اختياري، parent_ref اختياري، code، name، kind، display_order.
- kind: ZONE / BUILDING / WING / FLOOR / CLUSTER / SERVICE_AREA. null في بيانات قديمة يعرض «غير مصنف» ولا يصنف من الاسم.
- display_order: عدد صحيح غير سالب؛ ترتيب مستقر ثم code ثم id عند التعادل.
- parent_ref: null للجذر؛ المفقود في PATCH يبقي السابق، null يفصل عن الأب؛ لا ذاتية/دورة/مرجع خارجي أو مفقود.
- unit_groups: group_ref ثابت داخل المسودة؛ قالب، طريقة حجز، أسلوب اختيار، موقع، وحدات صريحة أو نمط أرقام واستثناءات، سعة وتفاصيل.
- إدخال units صريحة وpattern في المجموعة نفسها يرفض 422؛ لا دمج مبهم. التكرار يفحص بعد التطبيع بين جميع المجموعات والبيانات القائمة.
- التفاصيل الوصفية: bedrooms_count، bathrooms_count، notes. أعداد صحيحة غير سالبة عندما توجد؛ omitted غير معروف، و0 قيمة صريحة، ولا default يخترع غرفاً. نص آمن بحدود الحقول القائمة؛ الحدود الجديدة تثبت في العقد قبل التطبيق.
- capacity المطلوبة للبيع تطابق حدود المجال الحالية؛ لا يبدل null إلى 2 تلقائياً. يسمح حفظ مسودة ناقصة، ويمنع التنفيذ حتى معالجة الحقول المطلوبة للنمط المختار.
- existing IDs: UUID scoped مع إعادة القراءة؛ client_ref مرجع داخل المسودة فقط وليس بديلاً عن FK.
- صلاحية مسودة لا تعني جاهزية بيع؛ النواقص لها field_path وgroup_ref وcode قابل للترجمة.

### مصفوفة الإنشاء

الأسماء التالية رموز تصميم v2؛ يضيفها العقد صراحة ولا يمررها إلى enum v1 بلا مترجم.

| booking_mode     | مدخل مطلوب                                            | أثر التنفيذ                                                         | ممنوع                                           |
| ---------------- | ----------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------- |
| WHOLE_ONLY       | وحدة وسعة، اختيار EXACT أو CATEGORY                   | مورد واحد للوحدة؛ منتج منفرد أو فئة بمرشحين                         | توليد موارد من bedrooms_count                   |
| PARTS_ONLY       | أجزاء مسماة صراحة وسعة كل جزء، EXACT في الدفعة الأولى | هوية حاوية وعلاقة احتواء غير قابلة للبيع، موارد أجزاء ومنتجاتها فقط | منتج كامل تلقائي                                |
| WHOLE_AND_PARTS  | الأجزاء، سعة الكامل، إقرار مشاركة/وصول                | الأجزاء نفسها + منتج كامل وتركيبة مؤرخة                             | مورد كامل موازٍ للأجزاء                         |
| BEDS_ONLY        | غرفة حاوية وقائمة أسرّة/عدد صريح وسياسة مشاركة        | BED سعة1 وفئة أسرّة ضمن الغرفة                                      | منتج غرفة خاصة تلقائي                           |
| BEDS_AND_PRIVATE | مدخل BEDS_ONLY وسعة الغرفة الخاصة                     | الأسرة نفسها + تركيبة الغرفة الخاصة                                 | مضاعفة السعة بعد إضافة الكامل                   |
| CONNECTED_UNITS  | ≥2 existing resource IDs واتصال موثق وتاريخ           | منتج جديد وتركيبة؛ صفر موارد فعلية جديدة                            | اختيار عبر property أو استنتاج اتصال من التجاور |

القوالب ROOM/VILLA/APARTMENT/CABIN/TENT/HOUSE/SITE تعمل كاملة حسب الأنواع المتاحة فعلياً. SUITE_STANDALONE = WHOLE_ONLY على ROOM؛ SUITE_CONNECTED = CONNECTED_UNITS. DORM يقبل طريقتي الأسرّة فقط. GROUP المخصص للحجز الجماعي لا يضاف كطريقة هنا.

selection_mode: EXACT يحدد الوحدة الموعودة؛ CATEGORY يختار وحدة مكافئة ويثبت موارد الالتزام داخلياً وفق D-03، حتى لو تأخر تسليم رقمها للضيف. CATEGORY في الدفعة يقتصر على موارد كاملة متكافئة وعلى أسرة غرفة محددة؛ لا بدائل تركيبات أو مشاركة أسرّة بين غرف مختلفة ضمن فئة ضمنية.

في v1: EXCLUSIVE يحتفظ بمعناه، WHOLE_OR_PARTS يترجم WHOLE_AND_PARTS، BEDS يترجم بعد قراءة سلوك التنفيذ الفعلي، وSUITE القديم يبقى متصلاً. إذا كان التحويل غير حتمي تعرض «تحتاج مراجعة الإعداد» ولا تنفذ تخميناً. معادلة مقارنة v1/v2 يجب أن تثبت تماثل الموارد والمنتجات والأوراق، لا مجرد نجاح parsing.

## 4. العمليات والأخطاء والمعاملات

الأولوية لتوسيع عمليات SET الحالية. يثبت PSR-02 قائمة نهائية operationId→route→permission→DTO→test قبل أي controller جديد. لا ينشئ endpoint باسم مفترض إذا كانت القدرة موجودة.

| القدرة            | المسار المقترح                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| القوالب والمسودة  | ListSetupTemplates / GetSetupDraft / SaveSetupDraft / DiscardSetupDraft                         |
| المعاينة والتنفيذ | PreviewSetupApply / ApplySetupDraft                                                             |
| الاستيراد         | ImportSetupUnits؛ CSV القديم يبقى مدعوماً؛ لا رموز مركبة جديدة بلا مخطط مستقل                   |
| التغيير المؤرخ    | PreviewCompositionChange / ApplyCompositionChange بحسب حدود SET-06                              |
| شجرة المكان       | توسيع قراءة/إنشاء/تعديل المواقع القائمة؛ children pagination + ancestor path                    |
| بعد الإعداد       | عملية إضافة وحدات مستقلة أو إعادة استخدام مسار قائم يدعم ACTIVE بدليل؛ لا فك حماية مسودة مكتملة |

### القواعد الملزمة

1. GET قراءة فقط. previews قراءة فقط حتى إن كانت POST. جميع الكتابات تتبع CSRF/session الحالي.
2. authorize قبل replay، وإعادة فحص tenant/property والعضوية والصلاحية والحالة التشغيلية. صلاحيات المواقع وفق property.resource.manage كما أثبت جرد PSR-00، الموارد property.resource.manage، المنتجات/التركيبات وفق الصلاحية الفعلية القائمة التي يجردها PSR-00؛ العملية المركبة تتطلب اتحاد الصلاحيات، لا property.read.
3. If-Match يتضمن جيل المسودة والنسخة؛ غياب الشرط/قدم النسخة يطابق رموز SET القائمة. حفظ وحذف متزامنان لا يحييان جيلاً قديماً.
4. Idempotency-Key مطلوب للتطبيق والاستيراد والإنشاء المركب. الطلب المطابق يعيد الاستجابة المخزنة؛ نفس المفتاح بمحتوى مختلف 409؛ تغيير الترتيب غير الدلالي يطبع قبل hash مع الحفاظ على ترتيب العرض الدلالي.
5. ترتيب الأقفال يطابق منسق المشروع القائم ويثبت في البطاقة. قفل المنشأة يغطي إنشاء الشجرة/الموارد/المنتجات والنسخة؛ لا nested transactions تنفصل عن المعاملة الأصلية.
6. preview fingerprint تشمل النطاق، جيل/نسخة المدخل، المخزون، المواقع والإعدادات المتغيرة المؤثرة، الآثار/الحدود ذات الصلة. إضافة/إلغاء حجب مؤثر أو بلوغ limit يبطلها. الرفض PREVIEW_STALE=412 قبل كتابة أي كيان.
7. apply يعيد التحقق، يكتب العلاقات والموارد والمنتجات والتدقيق والإصدار وأحداث outbox المطلوبة في المعاملة نفسها، ويحفظ result للـreplay. فشل الخطوة الأخيرة يلغي الأولى.
8. لا قياس امتلاء دفعة بـعدد الفيلا فقط إذا ولدت أجزاء: الخطة تعد جميع الموارد والمنتجات والأوراق وأقصى عمق. تجاوز حدود التنفيذ يرفض قبل أي أثر؛ لا تقسيم صامت لدفعة ذرية.
9. حذف مسودة لا يحذف منشأة أو وحدات منشورة. الأرشفة ليست حذف تاريخ أو تغيير دفاتر.

أخطاء جديدة مقترحة عند عدم وجود رمز مكافئ: LOCATION_CYCLE، LOCATION_IN_USE، BOOKING_MODE_UNSUPPORTED، INVENTORY_TRANSFORMATION_REQUIRED. يوثق PSR-02 رمزها وHTTP في العقد وخرائط اللغات؛ المقترح 422 للقواعد، 409 لتعارض تعديل، 404 لمرجع خارج النطاق وفق سياسة عدم الكشف، و400 للنوع/البنية غير الصالحة. لا تغير رموز العمليات القائمة لتجميل الرسالة.

## 5. الهجرات والتوافق وخطة الاسترجاع

- PSR-03 يضيف parent_id/kind/display_order إلى location بصورة متوافقة. FK الأب تشمل tenant/property، والبحث مفهرس بالنطاق والأب والترتيب. منع الدورات يتحمل نقل A تحت B بالتزامن مع B تحت A؛ شرط تطبيق منفرد بلا قفل مشترك غير كافٍ.
- القيم القديمة تبقى جذوراً غير مصنفة. لا استنتاج طابق من «101»، ولا ربط بالاعتماد على تشابه الأسماء.
- display_label وتفاصيل الوحدة أعمدة/بيانات إضافية ذات schema مضبوط على الهوية الحالية؛ لا إسقاط code ولا إنشاء موارد بديلة. يجب ألا تجعل الحاوية قابلة للبيع لمجرد وجود capacity قديمة.
- snapshot قبل الترقية على قاعدة اصطناعية: مجموعات IDs، حالات النسخ، المراجع والأوراق، allocations، حصص القنوات، مفاتيح idempotency ومجاميع الدفاتر. المقارنة بعد الترقية تحفظ القيم المتعهد بها، لا الأعداد وحدها.
- اختبار قاعدة فارغة واختبار ترقية من مخطط سابق يحتوي حجوزات مستقبلية ونسخ RETIRED متعمدة. لا تعاد ACTIVE لاستنتاج خاطئ من التداخل.
- الرجوع قبل أي كتابة v2 يمكنه إسقاط إضافات فارغة فقط بعد تحقق. بعد كتابة شجرة v2: downgrade غير آمن يجب أن يرفض صراحة ويحافظ على سجل الهجرات؛ البديل forward fix أو restore ضمن نافذة توقف مفوضة.
- restore لنسخة أقدم بعد نشاط جديد ليس rollback مقبولاً بلا خطة حفظ/إعادة تطبيق النشاط ومطابقة القنوات. لا تشغل restore على dev المستخدم لاختبار الفكرة.
- المسودات المكتملة، الحجوزات والمالية ليست backfill لشجرة جديدة. أدوات الانتقال dry-run ثم خطة قابلة للتكرار بمراجع مصدر ثابتة.

## 6. واجهة لا تضلل المستخدم

تلتزم docs/99 §15؛ أربع خطوات، لا ظهور Resource/Composition للمستخدم. تحفظ اللغات الحالية ومفاتيحها ولا تضيف لغة جديدة.

- «كل وحدة بمفردها» هو الاختيار الابتدائي عند إضافة وحدة جديدة. لا تغيّر defaults لبيانات قديمة بطريقة تعيد تفسيرها.
- تعرض معاينة فورية للأسماء والأعداد؛ لا تعرض توفر مخزون محسوباً في المتصفح على أنه حقيقة خادمية.
- زر «حفظ الإعداد» منفصل عن بدء البيع؛ مؤشرات جاهزية الهيكل والأسعار والتشغيل والقنوات منفصلة.
- بعد الخطأ تبقى المدخلات؛ عند فقد الاستجابة يستخدم retry المفتاح نفسه. بعد تعديل مدخل الطلب تُنشأ عملية جديدة، ولا يعاد تدوير المفتاح.
- تبديل المنشأة يلغي/يتجاهل الرد المتأخر وتغيير draft_id يمسح preview؛ query keys تشمل tenant/property/schema/draft generation حيث يلزم.
- يستوعب النموذج إعادة تسمية، دفعة أرقام باستثناءات، أسماء حرة، ومجموعة ثانية مختلفة. لا جدول لكل ذرة في الشاشة الرئيسية؛ التفاصيل تُفتح عند الطلب.

## 7. طريقة التنفيذ للموديل الأقل قدرة

1. اقرأ PSR-progress واختر **أول مهمة غير منجزة ذات تبعيات ناجحة**. لا تعتمد على آخر رد محادثة فقط.
2. افتح بطاقة الحزمة وحدد المهمة والسلوك المتوقع وخريطة المستهلكين. لا تعالج حزمتين مستقلتين في تعديل واحد.
3. قارن العقد/DTO/service/DB/client/tests. سجل كل طبقة DONE أو N/A مع السبب وفق docs/95 §5.
4. نفذ أصغر تغيير يحقق الحالة؛ لا إعادة تسمية شاملة أو تعديل generated يدوياً أو ترقية مكتبات غير لازمة.
5. شغّل اختبار النجاح والرفض والتزامن المناسب؛ ثم check عند إغلاق حزمة كود. اختبارات PostgreSQL تحتاج build حديثاً وبيئة معزولة وفق docs/95.
6. دوّن الأمر وexit code والدليل والنسخة والحالة. فشل بيئي = ENV_BLOCKED، وليس PASS أو عيب تطبيق بلا تحقيق.
7. حدث البطاقة وسجل الاستئناف قبل الانتقال، بما يشمل الملفات التي تغيرت خارج الجلسة إن ظهرت؛ لا تتراجع عن عمل غيرك.
8. عند finding في العزل/الحصرية/التاريخ أوقف الجزء التابع، أصلح داخل النطاق وأعد فحص الحالة، ولا تؤجل P0/P1 إلى «تحسين لاحق».

حالات الحزمة: NOT_STARTED → IN_PROGRESS → IMPLEMENTED → VERIFIED_LOCAL → REVIEW_PENDING → ACCEPTED_LOCAL. NEEDS_FIXES تعيد العمل للنتيجة المحددة. لا يكتب المنفذ ACCEPTED_LOCAL لنفسه؛ القرار للمستخدم وفق سير العمل المعتمد. عند غياب مراجعة مستقلة يسلّم REVIEW_PENDING ويذكر ما بقي، ولا يدّعي اكتمال الخطة. العمل المستقل غير المتأثر يمكن أن يستمر ضمن التفويض.

## 8. حدود الجاهزية

الدليل جاهز لتوجيه تنفيذ تدريجي بعد تفويضه. PSR-00 وPSR-02 مهمتان مقصودتان لإغلاق ربط المواصفات بالكود وعقد OpenAPI؛ ليست دعوة لاختيار نموذج مجال جديد. أي اختلاف بين التصميم والكود يسجل بأثر وحل مقترح قبل تنفيذه. لا ضمان أن موديل أقل قدرة لن يخطئ؛ لذلك لا تُحذف المراجعة المستقلة أو الاختبارات العدائية.
