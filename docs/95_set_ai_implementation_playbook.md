## 1. طريقة الاستخدام

1. أعط المنفذ [رسالة البداية](96_set_ai_start_prompt.md) مع نطاق التفويض الفعلي.
2. يبدأ من [سجل المتابعة](execution/SET-progress.md)، لا من آخر رسالة محادثة وحدها.
3. ينفذ مهمة فرعية واحدة في كل دورة: يفهم، يحدد الأثر، يغير، يتحقق، يحدث السجل، ثم يتابع داخل التفويض.
4. لا تطلب منه تنفيذ الخطة كلها في تغيير واحد. لا يحتاج إذناً جديداً لكل مهمة روتينية داخل التفويض نفسه.
5. لا يعتبر إكمال القائمة دليلاً على الصحة دون نتائج وأثر فعلي قابل للمراجعة.

الدليل لا يضمن أن النموذج لن ينسى؛ يجعل التقدم والفجوات قابلة للكشف والاستئناف، ويمنع الاعتماد على ذاكرته وحدها.

## 3. قواعد لا يجوز تجاوزها

- نفس المستودع ونفس Stack وModular Monolith. لا إعادة بناء موازية ولا ترقية اعتماديات غير لازمة.
- افحص git status وتعليمات المجلدات قبل التحرير. الملفات غير المتتبعة قد تكون التطبيق كله؛ ليست ملفات يجوز حذفها. لا reset/clean أو كتابة فوق تعديل مستخدم.
- لا تبدأ تغيير المخزون قبل تحديد INV/CMP/D/AT المتأثرة.
- Controller ينقل ويتحقق من المدخلات؛ Application ينسق الصلاحيات والمعاملة؛ Domain يحمل القواعد؛ Persistence ينفذ الاستعلامات والقيود. اتبع نمط الوحدة القائم، ولا تعِد هيكلتها لمجرد توحيد أسماء الملفات.
- لا منطق صلاحيات أو جاهزية حاسم في الواجهة وحدها. لا أي اعتماد على tenant_id أو actor من body دون ربط بالسياق الموثوق.
- PostgreSQL يحمي المخزون. حافظ على منسق المعاملة والقفل الحالي لجميع الكتاب، بما فيهم workers؛ لا Redis أو cache كبديل للضمان.
- لا فصل كتابة المخزون عن الالتزام والإصدار والتدقيق وOutbox عندما تتطلب العملية ذريتها. لا اتصال خارجي طويل داخل معاملة قاعدة البيانات.
- Idempotency ليست ذاكرة محلية: إعادة الطلب لا تضاعف الأثر، وتعارض نفس المفتاح مع payload مختلف له خطأ محدد؛ يعاد فحص صلاحية صاحب الطلب قبل إعادة النتيجة.
- D-20 وUNKNOWN والسحب غير المثبت لا تتغير لتحسين UX. لا بيانات وهمية في استجابات نجاح.
- المال وفق D-14، والمنشور لا يعدل بصمت. لا تغيير العملة أو الوقت التاريخي كأنه تعديل اسم.
- لا تعطيل RLS أو validation أو test، ولا as any أو قيم افتراضية لإخفاء اختلاف عقد؛ يعالج السبب أو توثق ضرورة ضيقة بمراجعة.
- لا real guest data أو أسرار في الكود/fixtures/logs/screenshots. لا قراءة محتوى .env في المخرجات.
- لا شراء أو نشر أو تواصل أو قناة حية خارج التفويض. G-13 وEX تبقى كما هي دون أدلة وقرار مختص.

## 4. دورة تنفيذ ثابتة لكل مهمة

### قبل التعديل

اكتب بطاقة `docs/execution/SET-XX.md` عند بدء الحزمة. تحتوي: التفويض، السلوك المطلوب، السلوك الحالي بدليل ملف، حالات نجاح/رفض/فشل، المراجع، الملفات والمستهلكين، خطة الاختبار، وخطة ترحيل إن وجدت.

صغ المهمة مثل: «حفظ مسودة منشأة واستئنافها دون تكرار»، لا «تحسين الباك إند». إذا كانت تجمع أكثر من تغير سلوكي مستقل قسمها.

اقرأ المسار كاملاً: حدث الواجهة → API client → OpenAPI/DTO → Controller/guard → Application → persistence/SQL → الأحداث/workers → استجابة ومستهلكوها. استخدم rg للرموز وoperationId واسم الحدث والحقول. لا تكتف بملف واحد أو باستبدال نص شامل.

### أثناء التعديل

1. اكتب حالات القبول وخريطة الأثر أولاً.
2. عدّل مصدر العقد عندما يتغير السلوك العام؛ لا تغيّر الملفات المولدة يدوياً.
3. أضف الهجرة عند الحاجة واختبر الترقية والقيود.
4. نفذ القاعدة في المجال/الخدمة والمعاملة ثم API.
5. حدّث العملاء والواجهة واللغات والأحداث والاختبارات المرتبطة.
6. نفذ التحقق المناسب؛ أصلح الفشل ثم أعد الاختبار المتأثر.
7. راجع الفروق وحدّث السجل قبل الانتقال.

لا تنفذ خطوة SQL على قاعدة مستخدمة لمجرد وجود db:migrate. تحقق من هدف الاتصال دون كشف بياناته الحساسة، واستخدم قاعدة اختبار معزولة للترقية أولاً.

### بعد التعديل

املأ كل صف من قائمة الأثر أدناه بـDONE أو N/A مع سبب، وليس خانة فارغة. سجل الملفات والأوامر وexit code والنتائج ومسارات الأدلة. الفشل البيئي لا يساوي فشل المنتج ولا يساوي PASS.

## 6. بروتوكول تغيير قاعدة البيانات

1. اقرأ الهجرات ونمط RLS ومنح أدوار التشغيل في `packages/backend/src/persistence/migrations/`.
2. لا تعدل هجرة منشورة/مطبقة؛ أنشئ هجرة جديدة بأداة/نمط المشروع بعد التحقق من الاسم الفريد.
3. حدد نطاق tenant/property لكل جدول وعلاقة، وامنع FK عابر النطاق بقيود مناسبة، لا بشرط واجهة فقط.
4. اختر ترقية متوافقة: إضافة ثم backfill مضبوط ثم تحقق ثم فرض القيود؛ لا NOT NULL يكسر بيانات سابقة دون معالجة.
5. أي backfill قابل للإعادة ومحدود ومراقب. عدم إمكانية استنتاج الخصوصية من الاسم يعني طلب تصنيف، لا اختراع قيمة.
6. اختبر قاعدة فارغة وترقية قاعدة تحتوي بيانات اصطناعية قديمة، ثم قيود uniqueness/check/FK/RLS فعلياً.
7. افحص أثر الأقفال والاستعلامات والفهارس على بيانات تمثل الحجم المستهدف. لا تدعي أداءً دون قياس.
8. الرجوع لا يمحو معاملات حدثت بعد النشر. وثق forward fix والتوافق وخيار restore فقط مع شروطه وفقد البيانات المتوقع.
9. لا تطبيق على بيانات المستخدم ولا حذف «منشآت فارغة» ضمن تحسين الإعداد؛ هذا نطاق مستقل يحتاج فحص علاقات وتفويضه الموجود.

| واجهة             | تحقق متصفح فعلي للمسارات المتغيرة وRTL واللغات والهاتف؛ phase4 للمنشآت وphase7 للمكتب الأمامي حيث تنطبق |

في إغلاق حزمة كود شغّل `pnpm check` بعد الفحوص المركزة. هذا الأمر يتضمن build والعقود وtypecheck/lint/format ووحدات Jest؛ **لا يثبت نجاح أطقم PostgreSQL والهوية والتوزيع أو الاختبارات البصرية**.

مثال أمر مركز بعد استبدال المرشح باسم ملف موجود:

```bash
pnpm build
pnpm test:property:fast -- --filter=front-office-board --bail
```

`fast` لا يبني النسخة؛ لا تختبر dist قديمة بعد تعديل TypeScript. `pnpm test:property` يبني ثم يشغل المجموعة. لا تخترع اسم filter جديداً؛ تحقق من الملفات ومن تحليل arguments في المشغل.

قبل أطقم PostgreSQL: افحص سكربت الاختبار وهدفه ومنفذه. أوقف بيئة تطوير المشروع بـ`pnpm dev:stop` إذا كانت تتعارض مع الاختبار. عند PID مفقود والمنفذ مشغول، تحقق من PID وcwd والأمر وPGID قبل إنهاء عمليات المشروع فقط. لا pkill node ولا إعادة استعمال PID من سجل قديم. التزم بصلاحيات البيئة. بعد الانتهاء أعد الخدمات التي أوقفتها إذا كانت تعمل في البداية، ثم افحص صحتها.

سجل الأمر كاملاً ووقت التشغيل ونسخة الكود والنتيجة. عند pipe/tee تحقق من exit code الفعلي؛ لا تعتبر آخر سطر في log إثباتاً. لا تشغل أطقم تتنافس على المنفذ نفسه بالتوازي. لا تتوسع في الاختبارات بلا سبب بعد نجاح المطلوب.

عند التسليم المطلوب بالمشروع: `pnpm checksums` ثم `sha256sum -c CHECKSUMS.sha256`. نجاح البصمات يثبت سلامة قائمة الملفات فقط، لا صحة المنطق.

## 10. مثال إلزامي لفهم أثر الباك إند

المهمة: إضافة «معاينة إنشاء دفعة وحدات» ثم «تنفيذ الدفعة».

- المعاينة تحقق النطاق والأرقام والسياسة وتعرض الخطة؛ لا تكتب حجوزات أو تفتح البيع.
- التنفيذ يعيد التحقق من الصلاحية والنسخة والقيود داخل معاملة؛ لا يعتمد على ثقة بمعاينة قديمة.
- يحمي تكرار الطلب بمفتاح دائم، وفشل إنشاء منتج لا يترك مورداً قابلاً للبيع بلا ربط.
- إذا تغيرت المنشأة بين المعاينة والتنفيذ يرجع تعارض مفهوم مع خيار تحديث المعاينة.
- يحدّث OpenAPI/DTO والخدمة والقيود إن لزمت وclient والترجمات والاختبارات؛ لا يكفي إضافة زر.
- الاختبار: مدير يعاين، مستخدم آخر يضيف رقماً متعارضاً، الأول ينفذ: رفض آمن دون نصف دفعة. إعادة التنفيذ بعد التصحيح لا تضاعف الوحدات.

## 11. شروط التوقف والاستمرار

توقف عن الجزء المتأثر عندما يتطلب قرار مجال يغير D، أو فعلاً خارج التفويض، أو مورداً مفقوداً لا بديل له. اذكر السؤال المحدد والأثر، وأكمل العمل المستقل المصرح إن وجد. غياب معلومة روتينية يمكن استخلاصها من الكود ليس سبباً لنقل عبء التحقيق للمستخدم.

فشل اختبار بسبب الكود: أصلحه. فشل البيئة: سجل الخطأ وحقق سببه دون التحايل على sandbox. بلوغ حدود السياق: حدث تسليم الجلسة قبل نفادها، ولا تضع VERIFIED لتقليل العمل المتبقي.

## 12. حفظ الذاكرة والتسليم

حدّث سجل SET بعد كل مهمة مكتملة أو عائق جديد، وقبل نهاية الجلسة. بطاقة الحزمة تحتفظ بالتفاصيل؛ السجل ملخص حي وروابط، لا نسخ كامل للمحادثة.

قبل استئناف العمل: تحقق من الملفات الفعلية والعمليات الحالية ونتائج الأدلة؛ ملف السجل قابل للتقادم. لا تعيد اختبارات ناجحة لنفس النسخة بلا تغيير أو سبب، ولا تعتمدها إذا تغيرت الملفات المعنية.

قالب بطاقة الحزمة:

```text
الحزمة والمهمة الفرعية:
نطاق التفويض ومصدره:
الحالة والسلوك المطلوب:
المراجع CAP / INV / CMP / AT / D:
السلوك الحالي ودليل الملف:
معايير النجاح/الرفض/الفشل:
خريطة الأثر: كل صف DONE أو N/A مع سبب:
العقود/المهاجرات/المستهلكون:
الملفات المعدلة وسببها:
التحقق: أمر + نسخة + بيئة + exit code + نتائج + أثر نهائي:
أدلة المتصفح إن كانت واجهة:
الملاحظات المتبقية ومعرفاتها:
خطوة الاستئناف الدقيقة:
```

الحالات: NOT_STARTED، IN_PROGRESS، BLOCKED، IMPLEMENTED، VERIFIED_LOCAL، ACCEPTED. VERIFIED_LOCAL تحتاج الأدلة المطلوبة للحزمة؛ ACCEPTED يحتاج قرار القبول المختص، ولا يغير G-13. النتائج الجزئية تسجل صراحةً ولا تُرفع إلى حالة نجاح شامل.
