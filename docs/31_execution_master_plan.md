# خطة التنفيذ من الأساس إلى القنوات الخمس

التاريخ: 13 سبتمبر 2026. الحالة: خطة تنفيذ وتسلّم، وليست نتائج اختبارات أو تفويضاً جديداً بالنشر. أعدت بطلب المستخدم لتوجيه نموذج أقل تكلفة بحزم محددة. ترتيب المراحل وقرارات D-01..20 وثوابت المجال باقية كما هي. طلب إعداد هذه الخطة لا يبدأ كتابة كود المرحلة 2.

## ابدأ من هنا

عند الانتقال إلى نموذج جديد مباشرة، استخدم [رسالة البدء الجاهزة](36_next_model_start.md). تحدد تفويض إغلاق المرحلة 1 وتنفيذ المرحلة 2 فقط عند إرسالها له؛ بقية هذه الخطة تبقى المسار العام للمراحل اللاحقة.

1. اقرأ هذا الملف لتحديد المسار وحدود المنتج.
2. اختر أول حزمة قابلة للتنفيذ من [حزم العمل](32_execution_work_packages.md)، بعد فحص بوابتها وتفويضها.
3. استخدم [عقد قابلية التوسع](33_channel_extension_contract.md) لكل عمل في Distribution.
4. سلم للنموذج [تعليمات التنفيذ وسجل التقدم](34_implementer_handoff.md) مع معرف حزمة واحدة.
5. عند الوصول إلى المرحلة 13، اتبع [دليل الربط الحي](35_live_channels_runbook.md) لكل اتصال على حدة.

المصادر الحاكمة: [baseline](01_baseline.md)، [سجل القرارات](17_decisions_readiness.md)، [سياسات V1](23_v1_decisions.md)، [تصميم المخزون](24_inventory_design.md)، [البيانات](25_logical_model_contract.md)، [العقود](26_api_permissions_events.md)، [بوابات القبول](27_readiness_gates.md). الخطة تفصل التنفيذ ولا تستبدل هذه المصادر. عند خلاف مؤثر يفتح المنفذ بند تعارض محدداً قبل تغيير العقد المعني.

## نقطة البداية المثبتة

فحص المستودع في تاريخ الخطة: pnpm Monorepo موجود، React/Vite وNestJS وWorker وحزم مشتركة وأدوات PostgreSQL/Redis/Keycloak واختبارات الأساس. API المنفذ يعرض الصحة والجاهزية فقط؛ توليد أنواع عمليات V1 لا ينفذها. لا مخزون أو حجوزات أو صلاحيات مؤسسية أو اتصالات حية منفذة. [سجل المرحلة 1](29_phase1_verification.md) يسجل نجاح 35 اختباراً وقت تنفيذه، ولم نعد تشغيلها لمجرد كتابة هذه الخطة.

G-01 حالتها IMPLEMENTED / AUTOMATED_VERIFIED / VISUAL_PENDING. إغلاق فحص Computer Use هو أول حزمة؛ عدم توفر الأداة يسجل BLOCKED_TOOL_UNAVAILABLE ولا يستبدل بـPlaywright دون موافقة المستخدم. لا تعاد تهيئة المشروع أو تثبيت Stack مختلف لمعالجة هذا العائق.

## النتيجة المطلوبة

V1 بعد G-13: PMS تشغيلي متعدد العملاء والمنشآت، بصلاحيات مؤسسية، يعمل للسوق الإندونيسي بلغات ar وid-ID وen-US وعملتي IDR/USD، وتثبت فيه القنوات tiket.com وBooking.com وAgoda وTraveloka وTrip.com وفق حسابات مفوضة. لكل قناة استقبال إنشاء/تعديل/إلغاء، وربط أنواع وخطط، وتوفر وأسعار وفتح/إغلاق بيع، واستيراد ومطابقة واستعادة موثقة.

قبول القنوات الخمس يقاس على اتصالات اختبار/تشغيل مفوضة تمثلها جميعاً، وليس بافتراض أن لكل منشأة حسابات في المواقع الخمسة. لا إعلان دعم نوع مورد على قناة حتى يثبت تمثيله واختبار استمراره وحصريته. اتصال قناة واحدة pilot محدود، وليس اكتمال V1.

دعم الإقامة يشمل موارد الغرف والفلل والشقق والأسرة والمواقع والخيام والأكواخ والبيت والتراكيب المعرفة بحسب D-01/05. المراسلات والحجز العام والتوسع في المرحلة 14. المحاسبة العامة الشاملة والمشتريات والرواتب ليست متطلبات خفية لهذه الخطة؛ المالية التشغيلية المحددة في V1 مطلوبة.

## هندسة تمنع إعادة البناء

نفس المستودع ونفس Stack المعتمد في D-12. الإصدارات الموجودة والـlockfile نقطة الانطلاق؛ التحديث الأمني الضروري موثق ومختبر، ولا تحول حزمة أعمال إلى ترقية كبرى شاملة.

المسارات التالية مقترحة لملفات جديدة عند تفويض مرحلتها، وليست ادعاء أنها موجودة: `packages/backend/src/modules/<module>/{domain,application,persistence,adapters}`. الوحدات: identity، property، inventory، distribution، reservations، front-office، finance، operations، night-audit، reporting، saas. تبقى أساسيات المرحلة 1 في مواضعها إن لم تلزم نقلة. `apps/api` للنقل والجلسات، و`apps/worker` لتسجيل المستهلكين وتشغيلهم، و`apps/web` للشاشات، و`packages/contracts` لعقود النقل، و`packages/i18n` للترجمة.

Application ينسق معاملة مشتركة عند الحاجة، وكل وحدة تملك كتاباتها. Inventory هو المالك الوحيد للضمان؛ Distribution لا يكتب allocations عبر SQL مستقل، وFront Office لا يعدل Journal مباشرة. منسق التأكيد يجمع الحجز والالتزام ونسخة المخزون وAudit وOutbox في معاملة واحدة عبر واجهات الوحدات. لا تنشأ شبكة خدمات مصغرة أو منظومة plugins ديناميكية لهذا الغرض.

تطور schema حسب المرحلة: 2 تخزين البنية التحتية للقنوات ببيانات اصطناعية معزولة، 3 جداول الهوية وRLS، 4 المنشآت والموارد والعلاقات النهائية، 5 المخزون والأسعار، 6 الحجوزات، ثم جداول الوحدات الباقية. لا تنشأ جداول مستقبلية كاملة لتجاوز تبعية. المراجع التي لا يوجد مالكها بعد توثق كعقود غير مفعلة، وتستكمل بقيود وفحص orphan قبل الاستخدام التشغيلي.

## الضمان الداخلي وحدود البيع الخارجي

الثوابت إلزامية وليست خيارات يختصرها النموذج:

- قفل PostgreSQL على Property يجمع كل كتّاب الموارد والحصص والحجوزات والصيانة والتراكيب؛ لا Redis lock لضمان المخزون.
- مورد ذري واحد للفترة لا يملكه التزامان متعارضان، ولا يدخل Exposure متعارضة مع التزام أو حصة أخرى؛ قيد داخل جدول allocations وحده لا يحمي العلاقات بين الجداول.
- تثبيت مورد مستمر للإقامة، لا جمع أعداد يومية يمكن أن تمثل غرفاً مختلفة. Group وتعديل ونقل ينجحان ذرياً أو تحفظ الخطة السابقة.
- D-20 يحجز حصة المورد لقناة/عرض محدد. يجوز توزيع موارد مختلفة على الخمس؛ آخر وحدة لا تعرض في حصص متنافسة، والفيلا وأجزاؤها المتداخلة لا تنشر معاً.
- Open يرفع سبب منع محدداً، ولا يتجاوز صيانة أو حصة مجهولة. سحب الحصة لا يحررها بمجرد مهلة أو قبول HTTP؛ يلزم دليل ومطابقة.
- revision خارجي متعارض أو مجهول الربط يحفظ كاستثناء قابل للاستئناف؛ لا يحذف ولا يحول إلى حجز مؤكد بلا موارد. التأكيد الخارجي ليس ضماناً ذرياً من PMS.
- ACK منفصل عن قبول الإقامة؛ تحديثات ARI مطلقة ومؤرخة بالإصدار، مع فصل قبول المزود عن إثبات تطبيق القناة.

هذه السياسة تحد من انتشار الوحدة نفسها عبر القنوات. إذا لم يثبت المزود حصرية القناة وتمثيل الاستمرار ودليل السحب، يظل الاتصال المعني مغلقاً أو محجوب التفعيل وفق EX-01؛ لا يخفض النموذج الضمان ليعرض نتيجة ناجحة.

## جودة التنفيذ بنموذج أقل تكلفة

التكليف بحزمة واحدة في كل دورة، مع قائمة ملفات مسموحة وقراءة مركزة وعقد قبل التنفيذ. الحزمة الكبيرة تقسم إلى عقد/مجال، ثم persistence، ثم النقل/الشاشة مع بقاء البوابة مفتوحة حتى اكتمالها. لا يطلب من النموذج تنفيذ مراحل 2..13 في إجابة واحدة، ولا تعطى له كل المراجع التاريخية كتعليمات متساوية.

كل تسليم يثبت: ما تغير فعلاً، اختبار نجاح واختبار رفض واختبار فشل/تكرار مناسب، الأثر النهائي في DB حيث يلزم، رابط الأدلة، وما بقي. للمخزون والعزل والمال وACK/cutover يلزم مراجعة مستقلة في جلسة مراجعة منفصلة قبل إغلاق البوابة؛ تعالج صحة المنطق والاختبارات لا التنسيق. يجوز استخدام النموذج الأقوى لهذه النقاط فقط. لا تعد عبارة المنفذ «اجتازت جميع الاختبارات» دليلاً دون أمر ونتيجة ونسخة.

مع كل شاشة: مسار مكتمل إلى API فعلي، حالات loading/empty/error/forbidden/offline حيث تنطبق، نطاق منشأة ظاهر، عدم عرض نجاح تفاؤلي لحجز أو دفع أو مزامنة غير مؤكدة، العربية/الإندونيسية/الإنجليزية، RTL/LTR وتنسيق العملة والتوقيت، Computer Use مع الأدلة. [بروتوكول العمل](34_implementer_handoff.md) يحدد التوقف والاستئناف بدقة.

## المسار الخارجي والمدة

سجل EX-01..05 منفصل عن تقدم الكود. صاحب المنتج مسؤول عن العقود والتفويض والتكلفة؛ مسؤول المنشأة عن الحسابات والبيانات والمطابقة؛ المنفذ عن التكامل والأدلة؛ مختص السوق المخول عن ملف الضرائب والفاتورة والاحتفاظ. الأسماء الفعلية توضع في سجل التفعيل عند تعيينها.

لا يوجد موعد إطلاق أو تكلفة معتمدة. تقاس مدة الحزم الفعلية أولاً وتحدث توقعات المراحل بعد 3 حزم مكتملة؛ يفصل وقت التنفيذ عن انتظار المزود والفحص والمراجعة. يمكن إعداد النواة محلياً أثناء انتظار EX، لكن اكتمال الخمس يتوقف على أبطأ اعتماد مطلوب لها. لا يعوض اكتمال شاشة نسبة تقدم وظيفية غير مثبتة.

الخطوة التنفيذية التالية: P01-01 لإغلاق ما بقي من G-01، ثم P02-01 ضمن تفويض تنفيذ المرحلة 2. هذه الخطة بحد ذاتها لا تمنح صلاحية الشراء أو مراسلة المزود أو إنشاء حجز إنتاجي أو النشر.

## فحص حزمة الخطة

فحص توثيقي في 13 سبتمبر 2026: 58 حزمة رئيسية مرتبة من P01 إلى P13، مع خمس حزم تأهيل فرعية تحت P13-04. تحقق آلي من تسلسل المعرفات وعدم فقد حزمة، ومن 81 رابطاً محلياً عبر 36 ملف Markdown؛ لا روابط محلية مفقودة في هذا الفحص. نجح فحص Prettier للملفات المعدلة والمضافة. مقارنة بصمات الملفات السابقة حصرت التغييرات في README ووثائق التتبع/التسليم/البوابات؛ لا كود تطبيق أو عقد API أو اعتماديات معدلة.

هذا فحص للخطة وروابطها وتنسيقها فقط؛ لم يشغل اختبارات التطبيق أو Computer Use أو اختبار مزود حي. سجلات G وEX وAT بقيت بحالاتها الفعلية. بصمات الحزمة تحدث بعد إتمام التوثيق بأداة المستودع الحالية.
