# Reservation-driven Channex availability: current gap and bounded trial

Status: **LOCAL_OVERLAP_VERIFIED / RESERVATION_DRIVEN_ARI_NOT_IMPLEMENTED / AUTO_CLOSE_OPEN_NOT_TESTED**. This is a source audit and proposed test contract. The user stopped execution to start a fresh chat; the earlier demonstration-versus-indicator question is superseded. Future scope must be taken from the fresh-chat request; this document itself authorizes no implementation or provider mutation. G-13 remains NOT ACCEPTED and FUNCTIONAL BLOCKED. D-20, exposure guarantees and UNKNOWN handling remain unchanged.

Local overlap protection already exists. `packages/backend/src/modules/inventory/application/availability-service.ts` expands whole-Villa composition coverage to physical leaves and evaluates all required leaves. `inventory/persistence/guarantee-repository.ts:listOccupancyConflicts` checks ACTIVE plan allocations, blocks and RESERVED exposure allocations. `reservations/application/commitment-service.ts` confirms allocations per physical leaf and releases them on cancellation, with an inventory-version bump. This means a booked room prevents overlapping whole-Villa booking locally, and a booked whole Villa consumes its rooms. The operational trial has exercised local room/whole-Villa reservation paths; this is not evidence of provider closure or reopening.

The external automation path is missing. `commitment-service.ts:enqueueReservationEvent` returns immediately for a null channel connection, as normally used by DIRECT reservations. For a channel-linked reservation, confirm/modify/cancel events contain reservation IDs, item IDs, state and inventory version, without ARI cells. `distribution/application/dispatcher.ts:buildSnapshot` accepts an AvailabilitySnapshot or parses the other event as a RestrictionSnapshot; missing cells fail the minimum-one-cell contract in `distribution/domain/validation.ts`. It does not translate reservation events into channel inventory. `reservations/application/revision-service.ts` materialization bumps local inventory but does not publish derived ARI. A received booking can remain INQUIRY with no mapped product under existing rules; receiving it is not implicit confirmation.

`inventory/application/exposure-service.ts:enqueueExposurePublishEvents` can explicitly publish availability and open sale restrictions through the exposure workflow. Its resource reservations and withdrawal proof gates are intentional. The actual PMS staging receipt verified an explicit STOP_SELL outbox accepted by the provider and closed readback. It did not verify reservation-driven automatic close/open. The separate direct adapter price/zero-availability trial also supplies no such evidence. The existing single-ref closed-only staging worker rejects availability1 and stop_sellfalse; this guard must stay intact.

A future finite TEST trial requires a separately reviewed policy and exact catalog bindings, rather than widening that worker. Required inputs include the clone tenant/property/connection IDs; exact whole-Villa4 and three-room PMS product/composition/physical-leaf IDs; each corresponding external property/room/rate UUID; confirmed mapping versions; the selected night; fresh zero OTA channel counts; closed baseline readbacks; and a bounded authorization window. IDs are not invented here. Provider CRS revisions remain subject to their existing mapping/INQUIRY rules.

The trial must use **two separate sale modes**, with a closed verified transition between them:

- WHOLE mode: only the whole-Villa variant is eligible to open. All three room variants stay closed. A local whole-Villa reservation closes the whole variant; cancellation may reopen it only after canonical leaf availability, retained blocks and restrictions prove eligibility.
- PARTS mode: only room variants are eligible to open; the whole-Villa variant stays closed. A room reservation closes that room. Cancellation may reopen only that eligible room; another booked room remains closed. A local whole-Villa reservation must close every eligible room, and its cancellation recomputes their availability.

Start and every mode transition require no intersecting RESERVED, UNKNOWN or RECONCILING protected exposure, or a separately authorized complete release proof, which is currently unavailable. A provider closed GET alone never releases protected exposure. Existing allocation locks must never be bypassed to enable a local whole-Villa booking in PARTS mode.

Whole-Villa sale and intersecting room sale must never be simultaneously open, including in staging. A mode switch first closes all affected variants and verifies provider closure; UNKNOWN or failed closure blocks reopening in the other mode. This test does not establish generic production exposure release or relax D-20.

A proposed transaction hook would recompute affected variants under the existing property lock from canonical allocations/blocks/restrictions and enqueue absolute ARI cells with the same inventory version as the reservation mutation. The dispatcher would send only after commit through a dedicated finite scoped composition. Cancellation must recompute eligibility rather than blindly send availability1. Modify/replay tests must preserve idempotency and version fencing. The bounded policy must reject unrelated references/dates/properties, preserve adjacent-date readbacks, stop on ambiguous provider outcomes, and restore the reviewed closed baseline. No new price API, OTA activation, financial mutation, generic exposure release or webhook is part of this proposal.

Acceptance requires actual root-run evidence of local reservation mutation → committed derived outbox → provider acceptance → independent selected readback for both sale modes and both overlap directions. Include partial cancellation with another active room commitment, retry/replay stability and unchanged unrelated resources/finance. A UI indicator, if requested instead, must distinguish local availability, pending outbox, provider acceptance, verified readback and UNKNOWN; it cannot report automatic closure from a local inventory bump alone.
