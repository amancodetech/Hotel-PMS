## نتيجة دراسة العقود قبل التنفيذ

يوجد تغيير تركيب مؤرخ مدعوم: POST `compositions/:id/change-previews` ثم POST `compositions/:id/changes` بجسم effective_from/effective_to/resource_ids/preview_fingerprint ومفتاح idempotency. ينشئ نسخة جديدة ويحافظ على معرف النسخة القديمة وأوراقها؛ لا يوجد PATCH لتبديل أوراق النسخة القديمة. المصدر: `composition.controller.ts` و`composition-change-service.ts`.

اقتراح المنسق: مسار API محدود ومراجع لإضافة child إلى container موجود، أو توسيع عقد resource create لمرجع أب مضبوط النطاق والنوع والحالة ومنع الدورة. لا SQL أعمال، ولا حذف أو إعادة إنشاء V04. يلزم تفويض ملكية المصدر لهذا التغيير ومراجعته واختباره قبل كتابة سكربت mutation كامل؛ إعداد الخطة والقراءة المستقلة يمكن أن يستمرا الآن.

## التوسعة المحدودة ومصدر التنفيذ

اعتمد المنسق التصميم بعد مراجعة Astra: CREATE resource فقط يقبل parent_resource_id؛ child ROOM، وparent ACTIVE VILLA من النطاق نفسه وله ROOM children فعلية. property lock يسبق parent row lock. الفيلا الذرية ذات whole-only بلا غرف ترفض INVENTORY_TRANSFORMATION_REQUIRED؛ لا PATCH لنقل الأبوة ولا migration ولا إعادة بناء wizard. DTO يعرض الأب الفعلي دائماً، وحقل schema اختياري nullable لتوافق المستهلك السابق. إنشاء child يتطلب Idempotency-Key ويعيد نفس المورد قبل إعادة التحقق من حالة الأب الحالية؛ إنشاء مورد مستقل قديم لا يكتسب ضمان replay بمجرد إرسال header.

المصدر الخاص `correct-api.mjs` مستقل تحت `.local/verification/new-pratama-location-completion-20261009/`، ولا يعمل عند قراءة الوثيقة. هدفه حصراً hotel أو hotel_np_loc_complete_oct9. يثبت IDs والهدف ومصدره وخطته وإيصالات النسخة الاحتياطية والسلامة بالبصمات قبل الاتصال. تواريخ 2026-10-09..2031-10-08 قرار ثابت مفوض لهذه الجولة، وليست Date.now أو تمديداً تلقائياً.

متغيرات المنسق: NP_TARGET_DB وNP_API_DB_CONFIRMED وIDENTITY_TEST_DB متطابقة؛ NP_COMPLETION_APPLY=ADD_ONE_ROOM_COMPLETE_19_LOCATIONS_KEEP_HISTORY؛ NP_COMPLETION_PLAN_SHA256 وNP_COMPLETION_SOURCE_SHA256 لبصمات الملفات الحالية؛ NP_COMPLETION_BACKUP_RECEIPT/NP_COMPLETION_BACKUP_SHA256 وNP_COMPLETION_BASELINE_RECEIPT/NP_COMPLETION_BASELINE_SHA256 لإيصالات خاصة تحت .local/verification؛ NP_COMPLETION_BASELINE_CONFIRMED=96_RESOURCES_43_LOCATIONS_18_NULL_ZERO_MONEY_NO_RESERVATIONS بعد إثبات المنسق المستقل. NP_COMPLETION_STATE اختياري داخل المجلد الجديد؛ الافتراضي journal منفصل لكل هدف. السكربت لا يدعي إثبات المال أو الاستعادة بمجرد hash؛ هذه مسؤولية baseline/verify لدى المنسق.

الفحص المصدر المقترح للمنسق: node --check للمصدر الخاص، ثم build وتجربة PG بفلتر resources-parent-addition|resource-child-independent في runner الموجود. runner لا يستخدم --runTestsByPath. لا يصح إعلان نجاح أي فحص قبل إيصال root. بعد النجاح والمراجعة، يشغل المنسق node --env-file=.env .local/verification/new-pratama-location-completion-20261009/correct-api.mjs مع البيئة المثبتة، على clone أولاً.

سجل النية يحفظ الطلب قبل الشبكة والرد والقراءة المستقلة، ويكتب ذرياً ولا يغير ملفات الإيصالات القديمة. CREATE child/location وتغيير composition يعاد بنفس مفتاح replay؛ product/candidate POST القديم يحسم بالقراءة بعد فقد الرد، ولا يوصف بأنه idempotent. PATCH يعاد بعد قراءة الحالة والنسخة فقط. أي اختلاف خارج نطاق النية يوقف التنفيذ. VERIFIED_API_ONLY ليس قبولاً إنتاجياً أو فحص متصفح أو إثبات DB؛ النتائج المستقلة لدى root مطلوبة.

حراس ما قبل كل كتابة تقارن تفاصيل leaves/edges/header للتركيبات الأخرى دون تغيير، وتثبت أوراق وحواف نسخة Villa 4 التاريخية حتى بعد إغلاق نافذتها. تقارن candidates لكل المنتجات القديمة كاملةً؛ المنتج الجديد لا يقبل سوى candidate الغرفة الجديدة المطابق لنية مسجلة مسبقاً، دون صف إضافي غير مملوك.
