# PSR-03 — التشغيل والترقية والرجوع

## النطاق والقرارات

تطبيق PSR-D02/D04: المكان تنظيم جغرافي داخل المنشأة، وليس منتجاً أو مخزوناً قابلاً للحجز. لا يغيّر نقل المكان غرفاً أو تركيبات أو حجوزات أو أسعاراً. الكود الداخلي فريد داخل المنشأة؛ اسم العرض قد يتكرر (101 في مبنيين). تفاصيل غرف النوم والحمامات وصفية ولا تولّد موارد أو تزيد السعة.

الهجرة `Migration20260923120000_location_tree` إضافية: المواقع القديمة تبقى جذوراً بلا تصنيف، والوحدات القديمة تحتفظ بالهوية والكود والحالة والسعة. لا backfill من الأسماء. RLS والمنح القائمة مستمرة، مع FK للأب داخل الشركة والمنشأة. الحد الأعلى لمسار المكان32 عقدة، بما فيها الجذر. قفل المنشأة يسبق نقل العقدة؛ حارس قاعدة البيانات يمنع الدورات والعمق الزائد أيضاً.

## عقود الاستعمال

- `GET .../locations` يحتفظ بالقائمة القديمة. `?tree=true&parent_id=root&limit=25` يعيد الجذور، ومع UUID يعيد أطفال ذلك المكان و`ancestors` من الجذر إلى الأب المطلوب. `next_cursor` لا يعدل يدوياً.
- ترتيب الصفحات: display_order ثم code ثم id. أي تعديل للمواقع يبطل المؤشر بـSTALE_VERSION؛ المؤشر المنقول لنطاق آخر أو المعدل يرفض بـINVALID_REQUEST. مفاتيح توقيع المؤشر محلية للعملية، فإعادة تشغيلAPI تستلزم بدء القراءة من أول صفحة. هذه النسخة لا تدعي صلاحية المؤشر بين عملياتAPI مستقلة.
- `POST .../locations` يدعم parent_id/kind/display_order. وجود أي منها يتطلب Idempotency-Key. الإنشاء القديم code/name فقط يبقى متوافقاً. إعادة المفتاح بنفس المدخل تعيد نتيجة الإنشاء الأصلية؛ تغيير المدخل يرفض409.
- `PATCH .../locations/{id}` يتطلبversion الحالي. حذف parent_id من الطلب يحافظ على الأب، وnull يفصل العقدة إلى الجذر. لا يدعم تغييرcode. الأخطاء: INVALID_REQUEST للدورة/العمق، CROSS_SCOPE_REFERENCE للأب الخارجي، STALE_VERSION للنسخة القديمة.
- تعطيل مكان لا يغير وحداته أو حجوزاته. يمنع إسناد وحدات جديدة إلى المكان أو أي مكان تحته حتى إعادة تفعيله. المواردAPI والاستيراد وSET القديم تطبق ذلك.
- `display_label` نص1..160 أوnull؛ `unit_details` كائن يستبدل بالكامل عندPATCH، ويحتوي اختيارياً bedrooms_count/bathrooms_count (أعداد صحيحة0..100) وnotes حتى1000 حرف، دون مفاتيح أخرى. الإغفال يحافظ على القيم.
- CSV القديم `code,template,capacity,location` باقٍ. location هو كود المكان الفريد، وليس اسم العرض أو مساراً يستنتجه الخادم. UNKNOWN يشمل المرجع غير الموجود في المنشأة؛ INACTIVE يشمل سلفاً غير نشط. DRY_RUN لا ينشئ وحدات (يسجل استجابة التكرار كالسلوك السابق). APPLY يعيد التحقق وينشئ الصفوف المقبولة معاً؛ المرفوضة تبقى في التقرير. تعارض كود موجود يرفض المعاملة كلها، ولا إنشاء جزئي للصفوف المقبولة.

## الترقية المحلية

1. مراجعة نتائج قاعدة الاختبار المعزولة قبل أي قاعدة مستخدمة. تأكيد اسم الهدف دون إظهار سلسلة الاتصال أو الأسرار.
2. أخذ نسخة احتياطية قابلة للاستعادة وتسجيل إصدار التطبيق والهجرات. لا تخلط أدلة الاختبار الاصطناعية بقاعدة التشغيل.
3. إيقاف الكتاب أثناء نافذة الترقية. تطبيق الهجرة بالأداة المعتادة داخل معاملة. الأعمدة والفهارس تحتاج قفلDDL؛ زمنها على قاعدة الاختبار ليس وعداً لقاعدة كبيرة.
4. مقارنة IDs والكود والحالات والمراجع والتخصيصات وحصص القنوات ومجاميع الدفاتر قبل/بعد. فحص القوائم القديمة والجديدة بصفة مالك وقارئ ومنشأة أخرى.
5. تشغيل النسخة الموافقة للمخطط؛ عدم تشغيل النسخة الجديدة على قاعدة لم تطبق الهجرة، لأن المسارات الجديدة تعتمد على أعمدتها.

## الرجوع

- قبل وجود بيانات الشجرة أو تفاصيل الوحدات: down يقفل الجداول ويتحقق قبل أيDDL، ثم يزيل الإضافات فقط. اختبار down/up على قاعدة اصطناعية داخل معاملة يقارن القيم والسجل.
- بعد وجود parent_id أوkind أوdisplay_order غير صفري أوdisplay_label أوunit_details: down يرفع `PSR03_DOWNGRADE_BLOCKED` قبل تغيير المخطط. لا تمسح الأعمدة أو بياناتها ولا تعدل سجل الهجرات لتجاوز الحارس.
- الخيار الأول بعد بدء الاستخدام: إصلاح أمامي يحفظ البيانات. إن لزم رجوع كامل، اختبر استعادة النسخة الاحتياطية في قاعدة جديدة مستقلة أولاً، ثم قارنها ووثق المعاملات اللاحقة للنسخة وخطة استعادتها/مطابقتها. تحويل التشغيل يحتاج قراراً واعياً بفجوة البيانات؛ لا استبدال تلقائي لقاعدة المستخدم.
- لم ينفذ اختبار استعادة backup فعلي ضمن هذه الحزمة؛ المنفذ هو اختبارDDL/الرفض/حفظ القيم. خطة الاستعادة ليست ادعاء RPO/RTO جديد.
