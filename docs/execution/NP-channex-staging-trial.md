## Root execution and reconciliation

The coordinator loads only the private `.local/secrets/channex-staging.env` into its process. The script reads `CHANNEX_STAGING_API_KEY` or `CHANNEX_API_KEY` from the environment and never reads a credential file, prints keys, persists headers, or saves raw account responses. No account/user/contact information is copied to the receipt. Network target is hardcoded to the exact staging origin, catalog endpoint allowlist, and `redirect: error`; production and channel endpoints are inaccessible from this script.

Responses are streamed with a 2MB byte cap. List pagination is bounded to two requests within a property and five requests for account-wide collections. HTTP errors preserve only status, a known error-code allowlist, known schema-field names, and fixed validation phrases in private `provider-error-*.json`; arbitrary text, values and contact fields are redacted. Exceeding these bounds stops the tool and requires account-scope review rather than a raised automatic budget.

Commands below are prepared commands, not executed evidence. Choose one private mode0700 evidence directory and an actual current Asia/Jakarta operational start date. The coordinator runs the read-only plan first and reviews its full JSON, source digest, field gaps, existing catalog IDs and actual limits. The approved SHA256 is the exact plan file digest, not a user confirmation prompt; the user has already authorized this experiment.

```bash
node scripts/channex-staging-catalog.mjs plan --out .local/verification/NP-channex-staging-20261010 --start 2026-10-10
node scripts/channex-staging-catalog.mjs apply --out .local/verification/NP-channex-staging-20261010 --approve-plan-sha256 ACTUAL_REVIEWED_PLAN_SHA256
node scripts/channex-staging-catalog.mjs check --out .local/verification/NP-channex-staging-20261010
```

Apply/check use a persistent private `run.lock` to prevent concurrent or accidental repeat runs. After a completed or interrupted process, root must verify the recorded PID is no longer executing, preserve the lock as evidence, then explicitly clear the lock before check or resume. The lock is intentionally not automatically removed after a crash. A pending operation remains in the atomically persisted, fsynced mode0600 journal as **INTENT** until exact GET reconciliation succeeds. The script does not automatically retry POST, including timeouts, HTTP429/5xx, ambiguous responses, provider warnings, asynchronous ARI state, or lost create responses. An exact existing entity can be adopted after validating its description/fields and scoped relationship, even if the create response was lost. Duplicate exact titles, missing entities after prior intent, ID mismatch, unexpected rooms/plans, connected properties, source drift, and insufficient/missing actual limits all stop execution.

If an ARI intent is partially applied, GET closure cannot certify it and the script stops. Root records the observed state and proposes a specifically reviewed deterministic closure repair instead of blind replay. A successful later GET can reconcile an asynchronous task. Check never creates entities or opens sale; its only writes are private local journal/receipt evidence. No DELETE or general property update is implemented. A malformed or unverifiable provider schema is a reported gap rather than a reason to manufacture a successful result.

The private receipt reports the 100-date verification window. It is not permanent future closure assurance: dates rolling into the horizon still require a closure check before any future experiment. No guests, bookings, payments, imports, notifications, actual OTA connections, channel activation, or PMS connection/mapping/outbox mutations are part of this tool. No G-13 connection, D-20 handover proof, Booking.com/Trip.com/Agoda channel proof, certification, or production acceptance follows from creating this catalog.
