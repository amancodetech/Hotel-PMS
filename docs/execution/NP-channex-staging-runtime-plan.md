## Verified provider endpoints

The exact origin remains `https://staging.channex.io`, authenticated with the existing `user-api-key` mechanism. [Bookings Collection](https://docs.channex.io/api-v.1-documentation/bookings-collection) documents `GET /api/v1/booking_revisions/feed?filter[property_id]=PROPERTY_ID`, oldest-first ordering, `GET /api/v1/booking_revisions/:id`, and `POST /api/v1/booking_revisions/:id/ack`. ACK removes that revision from the feed. A shared key for 25 catalog properties must never fetch an unfiltered feed and reinterpret every revision using a single local connection.

[Booking CRS API](https://docs.channex.io/api-v.1-documentation/booking-crs-api) documents authenticated `POST /api/v1/bookings` and `PUT /api/v1/bookings/:booking_id`. The TEST property must first have the Booking CRS application installed. Create a uniquely tagged synthetic `ota_name: Offline` booking with known property/room/rate IDs, explicit dates, IDR dummy daily prices, two adults and no children/infants; omit deposits, guarantee/card data, taxes/services and real contact information. Save an INTENT before POST, then retain response booking/revision IDs; creation/modification are asynchronous and an immediate GET404 can precede visibility. After an unknown create outcome, reconcile via the scoped feed and booking tag; do not blindly create again. This trial does not impersonate Booking.com or any other OTA.

[PMS Certification Tests](https://docs.channex.io/api-v.1-documentation/pms-certification-tests) explicitly supports installing Booking CRS through Applications, then creating, editing and cancelling bookings from its UI as an alternative receiving test. For the first lifecycle, root may use that official authenticated UI for cancellation; an exact cancellation REST payload has not been independently verified here, so no guessed endpoint/body is proposed. Booking CRS availability changes and webhooks are real staging effects and must be reconciled. Keep the overlapping catalog closed, including constituent rooms of any whole-villa fixture.

[Availability and Rates](https://docs.channex.io/api-v.1-documentation/ari) documents POST `/availability`, POST `/restrictions`, GET `/availability?filter[property_id]=...&filter[date][gte]=...&filter[date][lte]=...` and GET `/restrictions` with the same scope plus `filter[restrictions]=rate,stop_sell`. Official successful writes return asynchronous task entries under `data` and warnings under `meta.warnings`. A task is provider acceptance only; GET must verify every requested cell before calling it provider state. It supplies no downstream OTA receipt or cutoff proof.

## Separate reservation-materialization gap

Transport inbox success is not a created PMS reservation. `distribution/application/inbox-store.ts` marks a new revision APPLIED after updating `distribution_external_booking`, without a reservation_ref. `reservations/application/revision-service.ts` returns DUPLICATE immediately for any APPLIED revision. Thus a normally stored revision cannot currently create its operational reservation through the reprocess route. This requires a separate explicit source batch across those two services and their meaningful PG integration tests; distinguish received/applied external state from materialized reservation state without weakening deduplication, financial isolation or inventory locks. The authorized existing route is `/tenants/:tenantId/properties/:propertyId/inbox/:revisionId/reprocess` (verify controller base path in the root runner).

The first minimum batch may legitimately prove provider transport plus persisted inbox/ACK and closed ARI; it must label operational new/modified/cancelled reservation behavior **NOT_PROVEN** until the materialization gap is repaired and tested. A fake reservation inserted by a runner would not close this gap.
