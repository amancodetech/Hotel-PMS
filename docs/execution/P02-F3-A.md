# إصلاح F3-A: استرداد ACK المستنفد مع وجود استثناء معالجة

التاريخ: 13 سبتمبر 2026، Asia/Makassar. المرجع: [مراجعة إكمال F1..F3](../40_f1_f3_followup_review.md). النطاق: المرحلة 2 فقط.

## الحالة

المراجعة المستقلة اللاحقة: **F3-A ACCEPTED ضمن نطاق الإصلاح المحلي** وفق [قرار المراجعة](../41_g02_review_acceptance.md). لا مانع متبقٍ مثبت في نطاقها، واستوفي شرط دخول P03. وصف REVIEW_PENDING التالي محفوظ كتاريخ تسليم المنفذ.

**REMEDIATED / REVIEW_PENDING.** عُولجت F3-A مع اختبارات ترقية وتزامن دائمة، وحُفظت إصلاحات F1/F2 وR1..R6. هذا تحقق ذاتي من المنفذ وليس مراجعة مستقلة؛ لا يبدأ P03.

## السبب

كان دليل «ACK المستنفد عولج» هو `inbox.exception_id IS NULL`، وهو حقل عام لاستثناءات المعالجة (MAPPING_MISSING وتعارضات revision). سجل قديم مستنفد مرتبط بـMAPPING_MISSING كان يُستبعد من الاسترداد رغم عدم وجود أي معالجة ACK له.

## الإصلاح

- مهاجرة جديدة `Migration20260913140000_distribution_ack_exception_link` تضيف عموداً مستقلاً `ack_exception_id` يفصل ارتباط استثناء ACK عن `exception_id` الخاص بالمعالجة، وتنقل إليه بأثر رجعي ارتباطات `exception_id` التي تشير إلى استثناءات ACK سابقة فقط (`ACK_EXHAUSTED/ACK_REJECTED/ACK_REQUEUED`) — دون مساس باستثناءات المعالجة.
- `listUnrecoveredExhaustedAcks` تكتشف الآن بـ`ack_exception_id IS NULL` مع `count >= maxAttempts` وlease NULL، بصرف النظر عن `exception_id`.
- الاسترداد يبحث عن أحدث استثناء `ACK_EXHAUSTED` للمراجعة **بأي حالة** عبر جدول الاستثناءات: إن وُجد يُربط دون إعادة فتح (حتى لو كان RESOLVED فلا يُفتح تلقائياً)، وإن لم يوجد يُفتح مرة واحدة ويُربط. لا تصفير للعدّاد ولا إرسال تلقائي ولا تحويل إلى SENT.
- `requeueAckRevision` يصفّر `ack_exception_id` فقط (بفاعل وسبب معلن ويسجل `ACK_REQUEUED`)، ويبقي `exception_id` وMAPPING_MISSING وحالته كما هما.
- sweep ونتيجة ACK في الخدمة يربطان عبر `ack_exception_id` كذلك، فلا تُستبدل استثناءات المعالجة بصمت.
- الملفات: `persistence/migrations/Migration20260913140000_distribution_ack_exception_link.ts`، `persistence/types.ts`، `persistence/inbox-repository.ts`، `persistence/exception-repository.ts`، `application/ack-service.ts`.

## اختبار الترقية والتزامن الدائم

`tests/distribution/integration/legacy-ack.pg.test.mjs` على قاعدة تُرقّى فعلياً من `Migration20260913120000_distribution_core` بعد زرع سبع حالات قديمة اصطناعية:

| الحالة القديمة | السلوك بعد الترقية |
|---|---|
| مستنفد بلا استثناء | يُنشأ `ACK_EXHAUSTED` واحد ويُربط، يبقى `UNKNOWN` بعدد 4 |
| مستنفد مع `ACK_EXHAUSTED` مرتبط بالحقل | المهاجرة تنقل الارتباط إلى `ack_exception_id`؛ لا يتكرر الاستثناء |
| مستنفد مع `ACK_EXHAUSTED` في جدول الاستثناءات فقط | يُربط الاستثناء القائم دون إنشاء ثانٍ |
| مستنفد مع `MAPPING_MISSING` مرتبط | يُنشأ `ACK_EXHAUSTED` مستقل ويُربط؛ `exception_id` وMAPPING_MISSING وحالة `EXCEPTION` محفوظة |
| SENT | لا تُمس ولا تُعاد معالجتها |
| FAILED | لا تُمس |
| PENDING غير مستنفد | يُرسل ACK مرة واحدة ضمن الحد |

- عاملان متنافسان (`Promise.all` على اتصالين) يستردان الحالات ثلاث مرة واحدة بالضبط (`recovered` مجموعهما 3)، والطلب القابل للإرسال يُرسل مرة واحدة.
- مرور ثانٍ وثالث متكرر: `recovered=0` و`processed=0`، وعدد استثناءات ACK لكل مراجعة يبقى 1.
- `requeueExhaustedAck` بحالة MAPPING: يعيد السجل `PENDING` بعدّاد 0 و`ack_exception_id=null` مع بقاء `exception_id` وMAPPING_MISSING مفتوحاً، ثم يرسل مرة واحدة ويصبح SENT، ويُسجل `ACK_REQUEUED` للتدقيق، ويبقى عدد `ACK_EXHAUSTED` واحداً.
- حمولة التحقق في `scripts/test-distribution.mjs` تشمل الآن وجود `ack_exception_id` وسبعة سجلات قديمة.
