# P12-01: خطط واستحقاقات وحدود وإصدارات سياسة وفوترة إدارية موثقة

الحالة: **IMPLEMENTED / VERIFIED محلياً** (15 فحصاً خاماً؛ 9/9 اختبار P12-01؛ 13 عملية Phase 12).
التاريخ: 17 سبتمبر 2026. المنفذ: جلسة P12 (بعد قبول G-11 محلياً وتفويض المستخدم بتنفيذ P12-01..P12-03).

## السلوك المنفذ وحدوده

- كتالوج خطط منصة `platform_plan` بترميز `^[A-Z][A-Z0-9_]{2,63}$` وحالة ACTIVE/RETIRED.
- إصدارات سياسة مؤرخة `platform_plan_policy_version` (limits + entitlements + notes) **append-only**:
  لا update/delete لدور التشغيل، trigger يمنع التعديل/الحذف، وقيد قاعدة بيانات يرفض أي
  `effective_from` سابق (`POLICY_BACKDATED` 422)، والإصدار التالي يجب أن يتقدم زمنياً عن السابق.
- اشتراك مستأجر واحد `platform_subscription` (PENDING/ACTIVE/SUSPENDED/CLOSED + version)، ويسجّل
  لقطة السياسة المثبتة (`policy_snapshot`) ونسختها واسم الخطة التجاري (`customer_label` مملوك للمنصة
  ولا يقرأ سجل `tenant`).
- استحقاقات `platform_entitlement` (ENABLED/DISABLED + limits + source PLAN/OVERRIDE) مع سجل حدث
  `platform_entitlement_event` مؤرخ append-only لا يمحو التاريخ؛ التعطيل لا يحذف الحدث السابق.
- قياس استخدام idempotent `platform_usage_event` بمفتاح فريد `(tenant, metric, idempotency_key)`
  وعدّاد `platform_usage_counter` (used/limit_value). الفرض **ذري في قاعدة البيانات** عبر دالة
  `public.platform_consume_usage()` التي تتحقق من نطاق المنادي ثم تنفذ
  `update ... set used = used + Δ where used + Δ <= limit returning`، فلا يمكن تجاوز حد مصرح
  حتى تحت سباق (الخاسر `422 LIMIT_EXCEEDED` ولا يتجاوز العدّاد حده).
- فُرض الحد على عملية منشأة حقيقية: `CreateProperty` يستهلك `PROPERTIES` ذرياً في معاملة الإنشاء
  نفسها (`enforceUsageLimit`)، فيرجع الإنشاءان المتزامنان عند الحد 201 و422 فقط، والعدّاد يساوي
  المقبول. غياب عدّاد معلن يعني لا حد معلناً (لا متر خلفي ولا ادعاء).
- فوترة إدارية موثقة `platform_invoice`/`platform_invoice_line` بترقيم `PINV-########`، عملة واحدة
  IDR/USD بلا أي تحويل (D-11/D-14)، مبالغ Decimal نصية وترحيل HALF_UP لمنزلتين، وإصدار idempotent
  بمفتاح `Idempotency-Key`، وإبطال بسبب موثق، وتسوية **سجل يدوي بمرجع** بلا بوابة دفع.
- اشتراك المنصة **لا يكتب** في `journal`/`journal_line`/`business_day`/`folio_charge`؛ أدلة الاختبار
  تقارن العدادات قبل/بعد وتتحقق من غياب أي قيد `PLATFORM%`.
- صلاحيات جديدة في الكتالوج: `subscription.read` (منشأة: TENANT_OWNER/TENANT_ADMIN/AUDITOR) و
  `platform.read`/`subscription.manage`/`platform.billing.manage`/`platform.support.manage`/
  `platform.support.read` (منصة فقط، MFA على الحساسة). أدوار المنشآت لا تحمل أي صلاحية منصة
  (لا rows في `role_permission`)، ودور المنصة لا يحمل أي صلاحية منشأة، والدور المنصة يُعرّف بالكود
  (`PLATFORM_ADMIN`/`PLATFORM_SUPPORT`) مع `platform_staff` وفحص `is_active_platform_staff` في RLS.
- قراءة منصة دنيا: `ListPlatformTenants` (P12-03) ستقرأ جداول المنصة فقط؛ لا قراءة مباشرة لسجل
  `tenant` إطلاقاً (منحة الدعم في P12-03 هي المسار الوحيد).

## تغيير API / schema / permission / event

- 13 عملية جديدة: ListPlatformPlans/CreatePlatformPlan/ListPlanPolicyVersions/CreatePlanPolicyVersion/
  ReadPlatformSubscription/SetPlatformEntitlement/RecordPlatformUsage/ListPlatformUsage/
  IssuePlatformInvoice/ListPlatformInvoices/VoidPlatformInvoice/SettlePlatformInvoice/
  GetTenantSubscription. لا تغيير لأي عملية قائمة ولا `operationId`.
- 6 أكواد صلاحيات جديدة؛ لا تعديل قوالب أدوار سابقة سوى إضافة `subscription.read` للقراءة.
- جداول جديدة فقط؛ لا تعديل أعمدة قائمة سوى قيد `tenant_status_check` (إضافة CLOSED).
- أحداث التدقيق: `platform.*` في `platform_audit_event` ومرآة على `audit_event` للمستأجر
  (plan/entitlement/usage/invoice). لا domain outbox جديد.

## Migration والترقية

- الترقية تصاعدية فقط على قاعدة تحتوي بيانات اصطناعية سابقة (طُبقت على قاعدة التطوير وعلى قاعدة
  اختبار تُنشأ من الصفر في كل تشغيل). `down` يعيد الحالة ويحذف الجداول/الدوال/الصلاحيات؛ لا حذف
  لبيانات منشآت. لا تعديل لأي مهاجرة مطبقة سابقة.

## العيوب المتبقية والحدود المعلنة

- سياسات الخطط/الحدود/الاستحقاقات/سياسة التعليق **قيم تشغيلية لم يحسمها المستخدم**؛ المنفذ آليات
  وسجل وقواعد حماية فقط، والقيم الحقيقية تُدخل لاحقاً بقرار المستخدم (لا قرار D جديد).
- فُرض الحد آلياً على `PROPERTIES` فقط ضمن P12-01 كعينة عملية؛ بقية المقاييس تُدار عبر
  `RecordPlatformUsage` ولوحة P12-03 (تعميم الفرض على كل كتابة موارد مؤجل بحدود معلنة).
- لا بوابة دفع ولا تحصيل إلكتروني؛ التسوية سجل يدوي بمرجع فقط.
- لا قراءة منصة لسجل `tenant` في P12-01؛ تقرر في P12-03 أن تمر عبر منحة دعم مؤقتة (SEC-006).
