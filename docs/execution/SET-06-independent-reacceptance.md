- **التاريخ:** 22 سبتمبر 2026.
- **النطاق:** إعادة قبول **SET-06: تنظيم الإعدادات، أثر التغيير، النسخ المؤرخة، ترحيل الموجود، والمطابقة** بعد حزمة الإصلاح، عبر إعادة إنتاج مستقلة لكل نتيجة في [المراجعة الأصلية](SET-06-independent-review.md) مقابل [تقرير الإصلاح](SET-06-fix-report.md) و[خطة الرجوع](SET-06-rollback-plan.md).

## 3) النتائج

### P1-RZ-06-01 — تواريخ تقويمية مستحيلة في cursor تعيد 500 (فئة متبقية من P1-5)

- **الموقع:**
  - `packages/backend/src/modules/property/application/setup-insights-service.ts:96-112` — `parseCursor` يتحقق بـ`Number.isNaN(Date.parse(createdAt))` فقط، و`Date.parse` يهرول تواريخ التقويم المستحيلة (مثل `2026-02-30` → 2026-03-02)، فلا يرفضها.
  - `packages/backend/src/modules/property/persistence/setup-insights-repository.ts:122-123` — القيمة الخام تُمرَّر إلى `?::timestamptz` فيسقط cast PostgreSQL بـ`22008`.
  - `apps/api/src/app.ts:64-76` — الخطأ غير مصنّف (`PropertyError`/`Zod`) فيرث `500 INTERNAL_ERROR`، و`101-123` يسجل `unhandled_error`.
- **الوصف:** أي cursor بشكل صحيح لكن بتاريخ تقويمي غير موجود يمرّ من التحقق ثم يفشل في قاعدة البيانات بدل أن يعود `400 INVALID_REQUEST`.
- **الدليل المستقل:**
  - سبر API مستقل (منشأة معزولة، مستخدم `admin`):

    ```json
    {"overflow-feb30":{"status":500,"code":"INTERNAL_ERROR"},
     "overflow-apr31":{"status":500,"code":"INTERNAL_ERROR"}}
    ```

    مقابل 9 حالات أخرى في المصفوفة نفسها عادت `400 INVALID_REQUEST` (منها المدخل الأصلي `2026-99-99Tbad|x`).
  - تعداد الفئة على PostgreSQL: `2026-02-30`, `2026-02-29`, `2026-04-31`, `2026-06-31`, `2026-09-31`, `2026-11-31` كلها `passesValidation=true` و`postgres=reject:22008`، بينما `2028-02-29` تمرّ عند الطرفين.
- **الأثر:** مدخل استعلام يخرق عقد الأخطاء (500 بدل 400)، ويلوث سجلات `unhandled_error` بلا كتابة بيانات — نفس أثر النتيجة الأصلية P1-5.
- **الإصلاح المقترح (أصغر تغيير):**
  1. في `parseCursor`، بعد regex، تحقق من تطابق مكوّنات التقويم (مثل `Date.UTC` مع إعادة فحص الشهر/اليوم، أو مقارنة `new Date(createdAt).toISOString()` بصيغة معيارية)، أو
  2. تغليف استعلام القائمة وتحويل `SQLSTATE 22008/22007` إلى `PropertyError('INVALID_REQUEST', { field: 'cursor' })`.
  3. إضافة حالات التقويم المستحيل (و`2028-02-29` كشاهد صالح) إلى اختبار المؤشرات الموجود في `tests/property/setup-changes.pg.test.mjs:1094-1119`.

لا توجد نتائج P0 جديدة، ولا نتائج على الخطة/الصلاحيات/العزل أُعيد فحصها؛ جميعها اجتازت (انظر §2).

## 5) الحدود والملاحظات المعلنة

1. **اعتماد 221000 على `audit_event`:** سجل المنشأ للتقاعد المقصود هو `composition.superseded` مع `after_safe.retired=true` و`before_safe.composition_id`. أعادت الجولة إنتاج هذا المسار بنجاح، لكن أي تقاعد مقصود أقدم لا يسجّل بهذا الشكل يبقى مراجعة يدوية (معلن في التقرير والخطة، ولم يتغير).
2. **idempotency محدودة بالعمليتين** (`composition.change.apply` و`setup.migration.apply`)؛ لا تعميم على باقي مسارات SET.
3. **خطة الرجوع:** المسار الأمامي (تصحيح أمامي) هو المُجرَّب فعلياً؛ سيناريو «استعادة نسخة سابقة لـ160000 ثم إعادة التقدّم» جُرِّب جوهره (بذر حالة ما قبل 160000 ثم replay حتى الرأس مع بقاء الحُرّاس)، لكن لم يُنفَّذ تمرين `pg_dump`/`restore` فعلي (يبقى ضمن EX-04/جولة الاستعادة، لا حكماً هنا). غموض نصي بسيط: بند الاستعادة يذكر «160000/170000 ثم 221000» ولا يذكر 180000/221100 صريحاً، لكن عبارة «حتى الرأس» تغطيهما؛ ولا يوجد `down()` آمن عند غياب نسخة احتياطية (معلن).
