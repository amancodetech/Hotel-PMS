## شروط تسليم البطاقة

1. كل مهمة لها دليل، وخريطة أثر docs/95 §5 مكتملة بـDONE أوN/A مبرر.
2. لا تعديل D/حدود العزل/المحاسبة أو الهجرات المطبقة، ولا تنفيذ امتداد مؤجل.
3. فشل تابع لمهمة سابقة يمنع إغلاق هذه البطاقة؛ لا mock لإخفاء API ناقص.
4. اختبارات التطبيق ليست مطلوبة لوثائق فقط؛ العقود والكود يحتاجان الفحوص الملائمة ثم check لإغلاق الكود.
5. الحالة النهائية لا تتجاوز الأدلة؛ ACCEPTED_LOCAL قرار المستخدم وفق سير العمل.

## 27 سبتمبر 2026 — استكمال الإضافة المستقلة والمحاكاة

بتفويض «حسنا اكمل» ثم «اكمل»: أُنجز مسار `?addition=1` للمنشأة SETUP/ACTIVE، يقرأ إعداداتها ولا يفتح مسودتها المكتملة. يتيح اختيار المواقع/الوحدات وطرق الحجز الست، ومعاينة الإضافة وتنفيذها؛ لا حفظ إلى مسودة الإعداد ولا تعديل للسعر/العملة/التوقيت/سياسة التشغيل. أزرار الإضافة والتأكيد منفصلة دلالياً عن حفظ الإعداد.

العقد SET صار **19 عملية**: PreviewSetupUnitAddition وApplySetupUnitAddition وSimulateSetupProduct إضافات منفذة، مع توليد الأنواع وفحص التطابق. الإضافة تعتمد نفس planner/writer ومعاملة واحدة وقفل المنشأة، وIf-Match خاص بالمنشأة والمخزون وبصمة نطاق/مدخل/شجرة/سياسة/حدود. الصلاحيات تُفحص قبل replay. تعارض مورد يلغي المواقع والمنتجات الجديدة. أُصلح تصادم أكواد المنتجات في الدفعات المتعاقبة التي تعيد استخدام group_ref: هوية خطة الإضافة مشتقة من المحتوى المطبع أيضاً. لم تتغير IDs أو أسماء المنتجات السابقة؛ أسماء المنتجات الجديدة تُشتق من أسماء/أكواد وحداتها بدلاً من group_ref الداخلي.

المحاكاة الجديدة للمنتج تستعمل resolveAvailabilityForProduct نفسه المستخدم للحجز، وتعيد AVAILABLE/UNAVAILABLE/SPLIT_REQUIRED/UNDETERMINED مع الوحدات التي ستستهلكها. تحقق تاريخ تقويمي/سعة/عدد/حد الإقامة والنطاق. لا إنشاء حجز أو hold، لا انتهاء سجلات أو تعديل مخزون، ولا اعتماد سعر أو سياسة نزيل أو فتح بيع. الواجهة تبطل النتيجة عند تغير المدخل وتهمل الرد المتأخر. محاكاة SET القديمة بقيت متوافقة دون تغيير.
