# الأساس الحاكم للمشروع

حالة هذا الملف: قرارات المستخدم المعتمدة، مع توضيحات مصدرها المحادثة. لا تغيّر دون توثيق.

تحديث تنفيذ 13 سبتمبر 2026: فوّض المستخدم كتابة كود المرحلة 1 وتثبيت الاعتماديات وتشغيل البيئة المحلية واختبارها، دون نشر أو شراء أو حسابات حقيقية. المنفذ ونتيجة G-01 في docs/29_phase1_verification.md. في الجلسة نفسها فوّض إكمال المتبقي وإغلاق G-01 ثم تنفيذ المرحلة 2 كاملة محلياً؛ نُفذت P02-01..06 وسجلت في docs/execution ونتيجتها G-02، ثم أُصلحت عيوب المراجعة المستقلة R1..R6 وسجلت في docs/execution/P02-R1-R6.md؛ ثم قبِلت المراجعة المستقلة G-02 محلياً (docs/41) ونُفذت المرحلة 3 محلياً P03-01..06 (هوية وجلسات وRLS وصلاحيات وواجهة) بحالة IMPLEMENTED / REVIEW_PENDING وفق docs/execution/G-03.md. لا تغيير في قرارات D أو ترتيب المراحل؛ P04 لا يبدأ قبل قبول G-03. نصوص منع البرمجة السابقة تصف ما قبل هذا التفويض ولا تعيد سؤاله.

- المنتج منصة SaaS للحجز والتأجير وخدمات الإقامة، وليس بيع العقارات.
- يدعم تصميمه الفنادق والمنتجعات والفلل والشقق والنُزل والمخيمات والمجمعات المختلطة والمجموعات وشركات الإدارة. مستوى التشغيل الفعلي لكل نوع تحدده القدرات المنفذة.
- Modular Monolith أولاً. حدود Domain واضحة؛ لا Microservices مبكرة.
- Frontend → API → Application → Domain → Persistence؛ لا منطق أعمال في Controllers.
- PostgreSQL، Redis، Queue/Workers، Private Object Storage، TLS، مراقبة وسجلات وتتبع ونسخ احتياطي.
- Shared Database + Shared Schema + tenant_id + RLS + تفويض تطبيقي. Tenant حد أمني وتجاري، Property حد تشغيلي. Dedicated Database لاحقاً خيار Enterprise.
- المنصة → Tenant → Hotel Group اختياري → Property. المستخدم يصل بالعضوية والنطاق؛ ليس بالضرورة تابعاً لقسم واحد.
- فصل Reservation وReservationGuest وStaySegment وRoomAssignment؛ تاريخ التخصيص لا يستبدل بصمت.
- أبعاد الغرفة مستقلة: الحالة الفيزيائية والتدبير والصيانة والتوفر والجاهزية.
- وحدات مركبة: تأجير الكل يمنع الأجزاء، والجزء يمنع الكل المتداخل، والموارد المشتركة لا تعد مخزوناً إضافياً.
- السجل المالي المنشور محفوظ؛ التصحيح Adjustment/Reversal/Refund/Credit Note. Idempotency للعمليات الحساسة.
- RBAC قابل للتهيئة مع Permission + Tenant + Property + Resource + Business State.
- الصلاحيات المؤسسية من متطلبات الإطلاق: أدوار ونطاقات منشآت دقيقة، منع تصعيد، فصل مهام واعتمادات، MFA وإبطال وتدقيق وفق D-18 وdocs/09_identity_security.md.
- Versioned REST API، أحداث ومهام غير متزامنة، Validation وError Model وPagination وRate Limits وAudit Metadata.
- Channel Manager Foundation في 2؛ Live OTA في 13. PMS مرجع المخزون. Official APIs أو مزود اتصال رسمي مع Adapter مستقل؛ لا Scraping كقاعدة منتج.
- أولوية الإطلاق الأولى هي ربط tiket.com وBooking.com وAgoda وTraveloka وTrip.com للحجوزات والتوفر وفتح/إغلاق البيع، وفق اتصال رسمي وقدرات مثبتة لكل قناة. هذا ترتيب أولوية لا تغيير لترتيب المراحل أو بواباتها، وفق D-16.
- منع الحجز المزدوج داخل PMS ثابت ذري يشمل كل موارد النطاق الحالية: الغرف والفلل والشقق والأسرة والمواقع والخيام والأكواخ، إضافة إلى الكل والأجزاء والتركيبات. عند قبول حجز يعاد اشتقاق المخزون وترسل النسخة الأحدث إلى جميع الاتصالات المتأثرة؛ التعارض الخارجي المحتمل يعالج فوراً كاستثناء ومطابقة لأن القنوات لا تشارك PMS معاملة ذرية واحدة.
- تجمع المنصة الحجوزات المصرح بها من حسابات القنوات المرتبطة في مساحة تشغيل واحدة. Guest Communications وحدة مستقلة ومتكاملة مع الحجز والنزيل والمهام والإشعارات؛ تنفيذ صندوق المراسلات الموحد مؤجل إلى ما بعد الإطلاق الأولي، حالياً ضمن توسعات المرحلة 14 وفق D-15.
- صلاحية الوصول إلى الحجوزات لا تعني صلاحية الرسائل. كل قدرة مراسلات تعتمد فقط على API رسمي أو مزود معتمد وصلاحيات الحساب، وتظهر القدرات غير المدعومة أو غير المصرح بها بوضوح دون ادعاء إرسال أو تسليم.
- العربية RTL والإنجليزية والإندونيسية LTR، توطين كامل وقابلية إضافة لغات.
- سوق الإطلاق إندونيسيا، واللغات ar وid-ID وen-US، والعملات IDR وUSD؛ فصل العرض والتحصيل والتحويل وتوقيت المنشأة وفق D-17 وdocs/21_indonesia_launch.md.
- Tenant isolation يشمل API وDB وJobs وCache وFiles وLogs وReports وSearch والإشعارات.
- Definition of Done: الوظائف والاختبار والتوثيق والعزل والتدقيق والرصد وقابلية النشر؛ العمليات الحساسة آمنة للتزامن والتكرار وإعادة المحاولة.

## أولوية المصادر

تفويض 12 سبتمبر 2026 بإكمال خطوات ما قبل البرمجة حسم نطاق V1 والسياسات في docs/23_v1_decisions.md وتصميم المخزون في docs/24_inventory_design.md. D-19 يختار Channex هدفاً تقنياً مشروطاً بالقبول والتحقق، لا اتصالاً منفذاً. D-20 يعتمد تعرضاً خارجياً محافظاً: المورد الذري للفترة لا يعرض في حصتين متنافستين، ولا يباع محلياً قبل سحب حصته الخارجية والتحقق والمطابقة. يمكن توزيع موارد مختلفة عبر القنوات الخمس؛ لا تباع الفيلا وأجزاؤها المتداخلة معاً. هذا يقلل الانتشار المتزامن لنفس الوحدة، ويظل ضمان القناة الخارجية محدوداً باستقلالها وتأخرها.

تفاصيل docs/22..27 وعقد OpenAPI تكمل هذه القرارات وتتقدم على التوصيات القديمة عند التعارض. V1 بعد بوابات 0..13، والتوسع والمراسلات بعده في 14 دون ترتيب داخلي مفروض. المتطلبات الخارجية EX-01..05 ليست محسومة بالتصميم. التفويض الأحدث يسمح بأساس المرحلة 1 وأدوات migrations فقط، وليس مخطط وحدات المراحل التالية أو الشراء والنشر.
